# 1. 为什么重构（v7 → v8）

v7 的核心问题不是 Agent 能力不足，而是 **Agent Framework 开始成为第二套 Product
Runtime**：Deep Agents / LangGraph 与 FastAPI Product Runtime 同时拥有
run、state、persistence、stream lifecycle 语义，形成重复状态机和重复真相源。

v8 的核心原则：

> **Product Runtime owns business truth; Agent Framework owns agent execution only.**

旧的 Deep Agents / LangGraph / LangChain / LangSmith runtime 已从 v8 代码、
依赖、Settings、数据库 schema 中完全移除，只保留在 Git 历史中。

## 持久化语义分离（v8 不变量）

```text
Conversation durability → PostgreSQL（business SOT）
Stream durability       → Redis Stream（后续）
Execution durability    → DBOS / Temporal（后续，M11 决策）
```

M5（LangGraph Production Persistence）已正式废弃（SUPERSEDED）：`AsyncPostgresSaver`、
checkpoint 表、thread 映射、`LANGGRAPH_*` 配置全部移除。**durability 需求本身
未消失**，只是重新分配到上述三层。

---

# 4. Product identity

```text
conversation.id → Product Conversation identity
request_run.id  → Product request/run identity
message.id/seq  → durable business message
```

业务表不保存 Agent Framework-specific identity：

- 无 `langgraph_thread_id`（已删除）
- 不允许 `pydantic_thread_id` / `agent_thread_id`

Business Conversation != Agent Runtime Thread；Business Message != Agent
checkpoint message。服务端只维护 `conversation.id ↔ request_run.id`。

---

# 5. Transport 与执行生命周期

```text
HTTP/SSE disconnect != Agent cancel
```

浏览器断开只影响 HTTP subscriber；真正 Stop 必须通过 Product Cancel API
（`POST /api/v1/chat/requests/{request_id}/cancel`），经 RequestRun →
Redis cancel signal → AgentExecutor。

RequestRun 状态机保持：

```text
running → completed | failed | cancelled
```

`cancelling` / `queued` / `stream_id` / `execution_id` 后续在
PydanticAI streaming/cancellation 接入时单独设计，不并入本次 clean baseline。
