这版的核心判断我会浓缩成一句架构原则：旧方案的问题是“Agent Framework 开始成为第二套 Product Runtime”；新方案的价值是让 PydanticAI 只做 Agent Execution，把 Run、状态、协议、持久化重新拆回各自该在的位置。


你批评得对。上一版写成了“PydanticAI 功能更多/更简单，所以换”，这不足以支撑一次**推翻已经确定架构**的重大决策。

真正的核心不是 Skills、SubAgent 谁都有，而是：

> **之前的方案已经开始出现“两个 Runtime、两个状态机、两个持久化语义、三层协议模型同时存在”的问题。PydanticAI 的价值，是让 Agent Framework 退回到它该处的位置：执行引擎，而不是变成第二套 Product Runtime。**

下面这版才是我认为应该进仓库的技术选型说明。

# ADR：Agent Runtime 从 Deep Agents / LangGraph 迁移至 Pydantic AI

**状态：Accepted**
**决策日期：2026-08-13**
**适用范围：Generic AI Platform / Travel Agent v7 后续架构**
**替代：Deep Agents + LangGraph + `@langchain/react` + Agent Streaming Protocol**
**采用：Pydantic AI + Pydantic AI Harness + Vercel AI SDK + FastAPI**

---

# 1. 这次不是“换框架”，而是在修正系统边界

这次技术选型变更不能简单理解为：

```text
Deep Agents 不够好
↓
Pydantic AI 更好
↓
所以换
```

这种解释是错误的。

真正的问题是：

> **随着 Product Runtime 逐渐完善，我们发现 Deep Agents + LangGraph 原方案和我们自己的 Product Runtime 在越来越多地方拥有重复的责任。**

我们的系统本来就已经有一套明确的产品级运行模型：

```text
Product Runtime
│
├── User / Auth / AuthZ
├── Conversation
├── Message
├── RequestRun
├── Idempotency
├── Rate Limit
├── Quota
├── Concurrency
├── Deadline
├── Cancellation
├── Usage Attribution
├── Billing
└── Audit
```

这些东西决定的是：

> 一个用户发起一次 Agent 请求以后，这次请求在“产品系统”里的完整生命周期是什么。

例如：

```text
RequestRun

created
   ↓
queued
   ↓
running
   ↓
completed

或者：

running
   ↓
cancelling
   ↓
cancelled

或者：

running
   ↓
failed
```

这已经是一套完整的 **Product State Machine**。

而原方案进一步引入：

```text
Deep Agents
↓
LangGraph
↓
thread
run
state
checkpoint
interrupt
stream lifecycle
```

于是系统逐渐出现第二套运行语义。

问题不是 LangGraph 做不到。

问题恰恰是：

> **LangGraph 做得太多，而其中一部分责任恰好已经属于我们的 Product Runtime。**

这就是整个技术选型变化最底层的原因。

---

# 2. 第一性原理：一个 Agent 产品真正需要哪几层

先不谈任何框架。

一个生产级 Agent 产品，本质上只有四类不同的问题。

```text
┌───────────────────────────────────────┐
│ 1. Product Runtime                    │
│                                       │
│ 用户、权限、RequestRun、Quota、计费     │
└───────────────────────────────────────┘

┌───────────────────────────────────────┐
│ 2. Agent Runtime                      │
│                                       │
│ LLM loop、tool、skill、subagent        │
└───────────────────────────────────────┘

┌───────────────────────────────────────┐
│ 3. Transport / UI Runtime             │
│                                       │
│ stream、tool UI、data part、resume     │
└───────────────────────────────────────┘

┌───────────────────────────────────────┐
│ 4. Infrastructure                     │
│                                       │
│ DB、Redis、durability、observability   │
└───────────────────────────────────────┘
```

理想状态是：

```text
每一层只拥有自己的语义。
```

也就是说：

```text
Product Runtime
不知道 Agent 内部怎么思考。

Agent Runtime
不知道用户是什么套餐。

UI Protocol
不知道 Agent checkpoint 怎么存。

Redis
不知道 Travel Agent 有哪些 subagent。
```

架构越接近这个状态，长期维护成本越低。

之前选择：

```text

+
LangGraph
+
AsyncPostgresSaver
+
Agent Streaming Protocol
+
@langchain/react
```

在当时是合理的。

因为我们需要的并不是简单：

```text
prompt
↓
LLM
↓
answer
```

而是：

```text
Agent
│
├── Skills
├── Tools

├── Planning

├── Streaming
├── HITL

```

Deep Agents 提供了高级 Agent abstraction。

LangGraph 提供：

```text
execution state
checkpoint
interrupt
stream
thread
```

`@langchain/react` 再提供前端运行时。

所以当时形成：

```text
React

```

在没有更短路径时，这是合理组合。

# 4. 但是随着 Product Runtime 完成，原方案开始产生“语义重叠”

这是推翻旧方案最重要的一点。

原方案最终不是只有一个 Runtime。

实际上形成了：

```text
               Product Runtime
                    │
                RequestRun
                    │
                    │
                    ▼
                Agent Runtime
                    │
              LangGraph Run
                    │
                    ▼
             LangGraph Thread
                    │
                    ▼
               Checkpoint
```

于是出现一个很难回答的问题：

> **到底哪个东西才是一次 Agent 执行的真正身份？**

我们已经有：

```text
request_id
```

LangGraph 又有：

```text
run_id
thread_id
```

协议还有：

```text
protocol runId
eventId
seq
```

最后很容易变成：

```text
conversation_id
request_id
langgraph_thread_id
langgraph_run_id
protocol_thread_id
protocol_run_id
stream_id
event_id
seq
```

每一个 ID 单独看都有理由。

但把它们放在一个产品里，意味着：

> **系统正在同时维护多个 Runtime identity model。**

这就是典型的 semantic impedance。

---

# 5. 第二个重叠：两套 State Machine

我们自己的：

```text
RequestRun
```

已经知道：

```text
queued
running
cancelling
completed
cancelled
failed
```

LangGraph 又有自己的：

```text
run lifecycle
graph state
interrupt
checkpoint
resume
```

于是会发生：

```text
RequestRun.status = running

但

LangGraph checkpoint = interrupted
```

或者：

```text
RequestRun = cancelled

但

graph task 仍然存在
```

或者：

```text
graph completed

但

assistant message 还没有成功 commit PostgreSQL
```

因此我们必须人为制定大量顺序规则。

例如之前我们已经不得不规定：

```text
先：

assistant message INSERT
RequestRun completed
COMMIT

然后：

emit lifecycle completed
```

为什么必须这么规定？

因为：

> **Agent Runtime 的 lifecycle 和 Product Runtime 的 lifecycle 不是同一个 lifecycle。**

一旦存在两个 State Machine，就必须写一层 reconciliation logic。

这不是 bug。

这是架构天然产生的复杂度。

---

# 6. 第三个重叠：两套持久化语义

旧方案中同时存在：

```text
PostgreSQL
│
├── Conversation
├── Message
├── RequestRun
└── Usage
```

以及：

```text
AsyncPostgresSaver
│
└── LangGraph State / Checkpoint
```

于是一个非常重要的问题出现了：

> **聊天历史到底以谁为准？**

例如：

```text
Conversation.messages
```

与：

```text
LangGraph checkpoint.messages
```

理论上应该相同。

但实际上它们属于：

```text
两个 transaction boundary
```

所以永远存在：

```text
A 写成功
B 写失败
```

的可能。

于是必须回答：

```text
谁是 SOT？
谁负责 recovery？
谁负责 reconcile？
```

如果回答：

```text
Business Message 才是 SOT
```

那 LangGraph Message State 就只是 execution state。

如果回答：

```text
LangGraph checkpoint 才是 SOT
```

那 Product Database 就无法独立解释业务。

两边都保存同一类信息，本身就说明：

> **Agent Framework 已经侵入 Product Persistence。**

---

# 7. 第四个问题：Streaming 又产生了第三套模型

LangGraph 原生输出：

```text
LangGraph Events / Stream Parts
```

但是浏览器不能直接使用。

因此旧方案需要：

```text
LangGraph Event
        ↓
Protocol Projector
        ↓
Agent Streaming Protocol
        ↓
Redis Replay
        ↓
SSE
        ↓
HttpAgentServerAdapter
        ↓
@langchain/react
```

这意味着我们自己必须理解和维护：

```text
message start
text delta
reasoning
tool start
tool delta
tool result
subagent
lifecycle
interrupt
custom event
namespace
checkpoint
error
```

然后映射为另一个协议。

我们阅读的 LangGraph + AI SDK 实践文档，本身就明确把：

```text
LangGraph Event ↔ UIMessageStream
```

定义为一个独立“桥接层”；它也承认混合方案带来的成本包括两套消息模型转换和桥接代码。 

这揭示了真正的问题：

> **只要 Agent Runtime 和 UI Runtime 不共享协议语义，就一定需要我们维护 Translation Layer。**

Translation Layer 本身并不可怕。

真正危险的是：

```text
它逐渐成为我们自己维护的一套 Agent Protocol implementation。
```

---

# 8. 所以旧方案真正的问题不是“组件多”

如果只是 package 多几个：

```text
deepagents
langgraph
langchain
```

其实无所谓。

真正的问题是：

```text
旧架构：

Product Runtime
拥有一次运行的业务语义

LangGraph
也拥有一次运行的执行语义

ASP
又拥有一次运行的协议语义

Frontend Runtime
又拥有一次运行的 UI 语义
```

结果是：

```text
同一个 run
有四种 representation。
```

我们要长期负责保证：

```text
Product Run
=
Graph Run
=
Protocol Run
=
UI Run
```

这才是旧方案最大的架构成本。

---

# 9. Pydantic AI 为什么从底层上解决了这个问题

Pydantic AI 最大的价值不是：

```text
它也支持 Tools
它也支持 SubAgents
```

而是它允许我们重新建立下面这个边界：

```text
Product Runtime
        │
        │ owns lifecycle
        ▼
RequestRun
        │
        │ invokes
        ▼
Pydantic AI Agent
        │
        │ returns events/results
        ▼
Product Runtime
```

也就是说：

> **Agent 再次变成一个 Executor，而不是另一个 Runtime Platform。**

调用关系重新变得非常简单：

```python
result = await agent.run(...)
```

或者：

```text
Agent Events
↓
Product Streaming Layer
```

Agent 不需要成为：

```text
Request identity SOT
Conversation identity SOT
Billing identity SOT
Product lifecycle SOT
```

这些继续全部归 FastAPI Product Runtime。

这正好符合我们的系统边界。

# 10. Pydantic AI Harness 改变了“必须使用 Deep Agents”的前提

如果 Pydantic AI 只是：

```text
LLM
+
tools
```

那我们不会换。

因为我们之前选择 Deep Agents 的真正价值在于：

```text
Skills
Planning
SubAgents
Memory
Filesystem
Dynamic Workflow
长期 Agent context
```

现在这个前提发生了变化。

Pydantic AI Core 明确把 Agent loop、model providers 和 capability/hook abstraction 放在 Core；官方 Harness 则作为可组合 capability library 提供更高级能力，而不要求修改 Agent framework 本身。([Pydantic][1])

现在：

```text
Agent
│
├── Capability A
├── Capability B
├── Capability C
└── Tools
```

而不是：

```text
Agent
↓
Deep Agent Runtime
↓
Graph Runtime
↓
Graph State
```

这是两种完全不同的组合哲学。

Pydantic AI Harness 的核心方式是：

```python
Agent(
    ...,
    capabilities=[
        Skills(...),
        Planning(),
        SubAgents(...),
    ],
)
```

能力是：

```text
Composable Capability
```

而不是新的 execution substrate。

Harness 当前已经明确包含 Skills、Subagents、Planning、Dynamic Workflow、Memory、Step Persistence 等能力。([Pydantic][1])

因此：

> **我们没有必要为了 Skills / Planning / SubAgents，再额外引入 Deep Agents + LangGraph 作为整个系统的基础运行时。**

这是推翻旧方案的第二个根本条件。

# 11. 为什么 Capability 模型更适合我们的产品

Travel Agent 将来可能出现：

```text
TravelAgent

+ Search
+ Weather
+ Map
+ Skills
+ Researcher
+ Planning
+ Recommendation
```

这些本质上都是：

```text
Agent 能力
```

而不是：

```text
Product lifecycle
```

因此最自然的模型应该是：

```text
Agent

capabilities=[
    skills,
    planning,
    subagents,
    ...
]
```

而不是为了增加一个 Researcher，修改：

```text
Graph topology
Graph node
Graph state
Graph streaming
Graph checkpoint
```

这会让：

```text
业务能力变化
```

尽量停留在：

```text
Agent Capability Layer
```

而不会穿透到：

```text
Execution Infrastructure Layer
```

长期维护成本明显不同。

# 12. 我们并不是否定 Graph

这一点必须说明。

LangGraph 非常适合：

```text
workflow topology 本身就是业务模型
```

例如：

```text
A
↓
B
├── approved → C
└── rejected → D
```

并且业务强依赖：

```text
node identity
graph state
checkpoint
time travel
explicit branch
```

这种情况下 Graph 本身就是 Domain Model。

那么引入 LangGraph 非常合理。

但我们的 Generic Agent / Travel Agent 核心并不是：

```text
固定 DAG
```

而更接近：

```text
Agent Loop

observe
↓
reason
↓
choose capability/tool/subagent
↓
execute
↓
observe
↓
continue
```

这是一个动态 Agent execution model。

因此让整个系统 Graph-first，并不是必须条件。

如果未来某个具体 workflow：

```text
Booking Workflow
Refund Workflow
Approval Workflow
```

确实需要 deterministic graph，

完全可以局部引入：

```text
workflow engine
```

而不是要求：

```text
所有 Agent
都必须运行在 Graph Runtime 上。
```

# 13. 第三个决定性变化：Pydantic AI 官方拥有 Vercel AI 协议 Adapter

这是技术选型真正发生转折的地方。

如果改成 Pydantic AI 后还需要我们：

```text
Pydantic Event
↓
自己设计 Protocol
↓
自己写 Frontend Runtime
```

那迁移价值会大幅下降。

但现在 Pydantic AI 官方直接提供：

```text
VercelAIAdapter
```

官方定义的职责就是：

```text
AI SDK request
        ↓
Pydantic AI run input
        ↓
Agent.run_stream_events()
        ↓
Pydantic AI events
        ↓
Vercel AI events
```

并且 FastAPI / Starlette 可以直接使用该 Adapter。([Pydantic][2])

于是协议责任变成：

```text
Pydantic AI
owns:

Agent Event
→ Vercel AI Protocol
```

我们不再 ownership：

```text
Agent Event
→ Browser Protocol Schema
```

这是一个巨大的架构变化。

# 14. 新方案真正减少的不是“代码行数”，而是 Protocol Ownership

旧方案：

```text
LangGraph
       │
       ▼
我们维护 Protocol Projector
       │
       ▼
Agent Streaming Protocol
       │
       ▼
@langchain/react
```

如果：

```text
LangGraph event schema 改了
```

我们改。

如果：

```text
Agent Streaming Protocol 改了
```

我们改。

如果：

```text
@langchain/react contract 改了
```

我们还要改。

新的方案：

```text

       │
       ▼
官方 VercelAIAdapter
       │
       ▼

       │
       ▼
useChat
```

协议 compatibility 的主要责任落到：

```text
Pydantic AI
+
Vercel AI SDK
```

而不是我们的业务团队。

这才是真正的“降低复杂度”。

不是：

```text
少写 500 行代码
```

而是：

> **少维护一条长期协议兼容链。**

# 15. 第四个决定性变化：AI SDK 把 UI Model 做成了稳定边界

前端真正关心的是：

```text
Message
Reasoning
Tool
Source
Data
File
Approval
Status
```

而不是：

```text
LangGraph node
checkpoint
namespace
state patch
```

AI SDK `useChat` 的核心模型是：

```text
UIMessage
└── parts[]
```

它直接描述：

```text
用户到底要看到什么
```

而不是：

```text
Agent 内部到底怎么执行
```

这非常重要。

因为 UI protocol 应该是：

```text
Product-facing
```

而不是：

```text
Runtime-facing
```

AI SDK 官方也明确支持非 JavaScript 后端实现其 stream protocol，并特别给出了 Python/FastAPI 作为 custom backend 的使用方向。([AI SDK][3])

Pydantic AI 再官方实现这层 Adapter。

因此新的边界非常清楚：

```text

→ Pydantic AI

→ AI SDK

Product semantics
→ FastAPI

Transport durability
→ Redis
```

# 16. Resumable Stream 的发现进一步证明这个分层是正确的

AI SDK 的 resumable stream 表面看只是：

```text
断线续传
```

但它实际上揭示了一个非常重要的架构事实。

AI SDK 官方要求 resumable stream 依赖：

```text
active stream tracking
+
Redis
+
POST create
+
GET resume
```

也就是说：

> **Stream 生命周期本来就应该独立于 Agent 生命周期。**

([AI SDK][4])

于是我们得到：

```text
Agent Execution
        ≠
HTTP Connection
        ≠
Conversation
```

这恰好和我们的 Product Runtime 设计完全一致。

---

# 17. 为什么 `Disconnect != Cancel` 是整个新架构的重要证据

AI SDK 当前官方还明确说明：

```text
resume
```

与 HTTP abort / `stop()` 存在冲突：

刷新页面、关闭 tab 或调用 `stop()` 都会触发 abort，从而破坏 resumable stream。([AI SDK][5])

这实际上证明：

```text
HTTP connection signal
```

不能天然等价于：

```text
Product cancellation signal
```

因此我们继续坚持：

```text
F5
网络切换
手机后台
SSE disconnect

        ↓

只代表 subscriber 消失
```

而不是：

```text
Agent.cancel()
```

真正 Stop：

```text
User Stop
↓
Product Cancel API
↓
RequestRun.cancelling
↓
Execution cancellation
↓
Agent / Model / Tool
```

换句话说：

> **Run lifecycle 属于 Product Runtime，而不属于浏览器 transport。**

这也是 Pydantic AI 方案与我们的 Runtime 边界高度契合的原因。

---

# 18. 第五个根本变化：Durability 可以从 Agent Framework 中解耦

旧方案中：

```text
LangGraph
↓
AsyncPostgresSaver
```

同时承担：

```text
Agent state
resume
checkpoint
```

这意味着：

```text
Execution Durability
```

与：

```text
LangGraph Runtime
```

强绑定。

但从第一性原理来看：

```text
Durability
```

其实是基础设施能力。

它不应该决定：

```text
Agent 必须是什么框架。
```

现在 Pydantic AI 已经正式提供 durable execution integration，包括 DBOS、Temporal、Prefect 和 Restate。([Pydantic][6])

DBOS integration 更能说明新的设计哲学：

```text
普通 Agent
+
DBOSDurability Capability
+
DBOS workflow

→ durable Agent
```

也就是说 durability 是：

```text
Capability
```

而不是：

```text
Agent Runtime 本体。
```

当前 Pydantic AI 已经把 DBOS durability 作为 capability 暴露，模型请求、MCP 等 I/O 可以被路由到 durable steps；只有在 DBOS workflow 内运行时才获得 durable semantics。([Pydantic][7])

这和我们希望的架构非常一致：

```text
Agent
仍然是 Agent

Durability
是可插拔 Infrastructure。
```

---

# 19. 这让三种“恢复”终于可以彻底分开

之前非常容易把：

```text
checkpoint
message persistence
stream replay
```

全部称为“恢复”。

实际上它们是三个完全不同的问题。

```text
Conversation Durability

用户明天打开页面
还能不能看到昨天聊天？
```

由：

```text
PostgreSQL
```

解决。

---

```text
Stream Durability

Agent 正在生成
浏览器 F5
回来能不能继续看？
```

由：

```text
Redis Stream
```

解决。

---

```text
Execution Durability

FastAPI 进程整个挂了
Agent 能不能继续？
```

由：

```text
DBOS / Temporal
```

解决。

因此：

```text
Conversation Durability
≠
Stream Durability
≠
Execution Durability
```

一旦把这三个问题分开，

就会发现：

> **为了 Conversation persistence 和 Stream replay，没有理由要求整个 Agent 建立在 LangGraph Checkpoint Runtime 上。**

# 20. Redis Stream 为什么还保留

换 Pydantic AI 并不是：

```text
所有基础设施全部删掉。
```

Redis Stream 仍然非常重要。

但职责发生了巨大简化。

以前 Redis 存：

```text
Agent Streaming Protocol Event
```

而它前面还有：

```text
LangGraph
↓
Protocol Projector
```

现在可以变成：

```text
Pydantic AI
↓
VercelAIAdapter
↓
Vercel AI Events
↓
Redis Stream
```

Redis 只负责：

```text
append
cursor
replay
subscriber
TTL
```

它完全不需要理解：

```text
Agent state
Graph
SubAgent
Checkpoint
```

这就是一个干净的 Infrastructure component。

# 21. 第六个根本变化：Pydantic AI 与我们的 Python Product Runtime 共享同一种类型系统

这个原因比“Python 写起来舒服”更深。

我们的后端已经建立在：

```text
FastAPI
Pydantic
SQLAlchemy
Python async
```

上。

Pydantic AI 又使用：

```text
Python type hints
Pydantic models
typed dependencies
typed outputs
```

因此：

```text

↓
Product DTO
↓
Agent dependencies
↓
Tool input
↓
Structured output
↓
Persistence DTO
```

可以处于同一套 type system。

Pydantic AI 自身也明确把 fully type-safe 和 FastAPI-like Python ergonomics 作为核心设计目标。([Pydantic][8])

这意味着我们不需要大量：

```text
LangChain object
↔
Product Pydantic model
```

转换。

减少的不是 syntax。

而是：

```text
Boundary Type Conversion。
```

# 25. 这才是为什么 Pydantic AI 比 Deep Agents 更适合当前项目

不是因为：

```text
Pydantic AI 更新
```

也不是因为：

```text
Pydantic AI 最近火
```

更不是因为：

```text
它 API 更漂亮
```

而是：

> **随着我们的 Product Runtime 逐渐成熟，我们需要的是一个“更薄的 Agent Runtime”，而不是一个继续向上承担 Product Runtime 责任的 Agent Platform。**

Deep Agents + LangGraph 很强。

但强大的代价是：

```text
它本身也拥有
state
thread
run
checkpoint
stream
interrupt
lifecycle
```

对于没有自己 Runtime 的应用来说，这是优势。

但对于已经有：

```text

Cancellation
Quota
Usage
Billing
```

的系统来说，

其中一部分会开始重叠。

而 Pydantic AI 的：

```text
Agent
+
Capabilities
+
Harness
```

模型更容易被嵌入我们自己的 Runtime。

这是两者对当前项目最大的不同。

更符合系统边界。

# 27. 为什么现在才换，而不是一开始就选 Pydantic AI

因为架构决策永远依赖当时的前提。

最开始，我们认为获得：

```text

Frontend Agent Streaming
```

最短路径是：

```text
Deep Agents
+
LangGraph
+
@langchain/react
```

因此旧决策合理。

后来连续出现四个改变决策的事实：

```text
Pydantic AI Harness
成熟到可以覆盖我们真正需要的高级 Agent 能力

+

Pydantic AI 官方 VercelAIAdapter
解决 Python Agent ↔ AI SDK Protocol

+

AI SDK Resumable Stream
把 Stream Durability 明确放到 Redis / Transport Layer

+

Pydantic AI Durable Execution
让 Execution Durability 不必绑定 LangGraph
```

这些变化不是：

```text
多了几个 feature
```

而是：

> **它们一起改变了“完成同一套系统需要多少层 Runtime”这个问题的答案。**

以前：

```text
Deep Agents + LangGraph
```

是满足需求的较低复杂度方案。

现在：

```text
Pydantic AI + Harness
```

可以在更少 Runtime 层的情况下覆盖同样的核心需求。

因此继续坚持旧架构反而变成：

```text
因为已经决定过
所以继续维护历史复杂度。
```

这不是合理的架构原则。

# 29. 被推翻的其实不是 Deep Agents

最终应该准确描述这次决策：

```text

Deep Agents 不适合 Agent。
```

真正得出的结论是：

```text
Deep Agents + LangGraph

作为一个完整 Agent Runtime Platform

与我们已经建立的 Product Runtime

存在越来越明显的职责重叠。
```

```text
Pydantic AI
+

```

提供了更适合：

```text
“嵌入已有 Product Runtime”
```

的模型。

# 30. 最终决策原则

这次选型最终依据的不是功能数量，而是下面这个原则：

> **Product Runtime 必须只有一个。**

Agent Framework 可以拥有：

```text
reasoning
tool loop
skills
subagents
planning
```

但不能逐渐成为第二个：

```text
Run SOT
Conversation SOT
Lifecycle SOT
Persistence SOT
Protocol SOT
```

我们的系统应该始终保持：

```text
Product Runtime owns business truth.

Pydantic AI owns agent execution.

AI SDK owns UI protocol.

Infrastructure owns durability.
```

当这个边界成立时：

```text
任何一层未来都可以独立替换。
```

这是选择 Pydantic AI 真正的架构原因。

---

# 31. 一句话结论

之前方案的问题不是：

```text
Deep Agents 功能不够。
```

恰恰相反：

> **它提供了一套过于完整的 Runtime，而我们自己也正在建设一套完整 Product Runtime。**

最终导致：

```text
两个 Runtime
两个 State Machine
两个 persistence model
多套 run identity
多层 streaming translation
```

Pydantic AI + Harness 的价值，是把 Agent 层重新压缩成：

```text
一个可嵌入、可组合的 Execution Engine
```

同时借助：

```text
VercelAIAdapter
AI SDK
Redis Stream
DBOS
OpenTelemetry
```

把：

```text
UI Protocol
Stream Durability
Execution Durability
Observability
```

分别交回它们真正所属的层。

**所以这次不是因为 Pydantic AI“更强”而换。**

而是因为：

> **Pydantic AI 让整个系统重新获得了单一 Product Runtime、单一业务真相源和清晰的责任边界。**

这才是推翻旧方案的根本理由。

这版的核心判断我会浓缩成一句架构原则：**旧方案的问题是“Agent Framework 开始成为第二套 Product Runtime”；新方案的价值是让 PydanticAI 只做 Agent Execution，把 Run、状态、协议、持久化重新拆回各自该在的位置。**
