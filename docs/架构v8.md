## 0. 执行摘要

本架构的核心决策只有一句话：

> **Product Runtime 与 Agent Runtime 在逻辑 ownership 上彻底分离，但当前物理部署保持同进程/同容器的模块化单体；Product Runtime 是唯一业务控制面，PydanticAI 只是可替换的 Agent execution engine。**

最终技术栈：

```text
Frontend Framework           React 19 + Vite 8
Routing / Server State       TanStack Router + TanStack Query
Generic UI                   Tailwind CSS + shadcn/ui
AI UI Primitives             AI Elements（优先，Vite 兼容性需 Package Gate）
AI UI Runtime / Protocol     Vercel AI SDK UI / @ai-sdk/react / useChat
Product Runtime              FastAPI
Agent Port                   AgentExecutor Protocol
Agent Framework              PydanticAI
Agent Harness                Pydantic AI Harness（版本固定 + 本地 adapter 隔离）
Model Gateway                LiteLLM Proxy
Business SOT                 PostgreSQL
Coordination                 Redis
Stream Replay                Redis Streams（M8 Production Streaming）
Execution Supervision        In-process ExecutionSupervisor（M8，非 crash-durable）
Execution Durability         DBOS（未来，满足触发条件后引入）
Observability                OpenTelemetry-first，后端可替换
```

架构不是：

```text
React → AI SDK → FastAPI → LangGraph/Deep Agents → Checkpoint
```

也不是：

```text
React → Hono → FastAPI → PydanticAI
```

而是：

```text
React / AI SDK
      ↓
FastAPI Product Runtime
      ↓
AgentExecutor
      ↓
PydanticAI + Harness
      ↓
LiteLLM
```

Product Runtime 负责“这次请求在产品中是什么”；Agent Runtime 负责“这次请求如何完成智能执行”。两者不得互相夺取 SOT。

# 2. 第一性原理与核心架构原则

## 2.1 Single Product Runtime

系统只能有一套业务运行语义。

Product Runtime 拥有：

```text
User / Auth / AuthZ
Conversation
Message
RequestRun
Idempotency
Rate Limit
Quota
Concurrency
Deadline
Explicit Cancellation
Usage Attribution
Billing
Audit
Retention / Delete Policy
```

任何 Agent Framework 都不得成为这些概念的 SOT。

## 2.2 Agent Runtime 是 Execution Engine，不是 Product Platform

PydanticAI 拥有：

```text
Agent loop
Model calls
Tools / Toolsets
MCP
Structured output
Dependencies
Capabilities / Hooks
Skills
Planning
Subagents
Agent-local context management
```

它不拥有：

```text
用户套餐
Conversation ownership
RequestRun 状态
业务幂等
业务计费
业务历史 SOT
产品 cancel 权限
```

## 2.3 逻辑分离，物理先不分

当前阶段采用：

```text
Modular Monolith

FastAPI process/container
├ Product Runtime
├ AgentExecutor port
└ PydanticAI implementation
```

而不是现在就：

```text
FastAPI Product API
    ↓ RPC
Agent Microservice
```

只有出现独立 autoscaling、长任务、sandbox、GPU、故障隔离、独立发布周期等明确需求时，才物理拆分 Agent Worker。

## 2.4 Business Durability、Stream Durability、Execution Durability 三分

```text
Business durability  → PostgreSQL
Stream durability    → Redis Streams
Execution durability → DBOS / Temporal 等（未来）
```

它们不是一件事，不能用一个 checkpoint runtime 包办。

## 2.5 Transport Disconnect != Product Cancel

浏览器刷新、网络断开、SSE 断开，只结束 subscriber；不得天然等价于终止 Product Request。

真正的 Stop：

```text
POST cancel
→ ownership check
→ Product Request terminal/cancel signal
→ Agent cancellation token/task cancellation
```

## 2.6 Product DB 禁止出现 Agent Framework Identity

禁止：

```text
langgraph_thread_id
pydantic_thread_id
agent_thread_id
framework_run_id
```

Product identity 固定为：

```text
conversation.id
request_run.id == request_id
```

如未来 execution engine 需要额外执行 ID，只能作为可替换 infrastructure mapping，并优先挂在 RequestRun execution metadata，而不是污染 Conversation。

## 2.7 Frontend 同样只能有一套 Active AI Runtime

采用：

```text
TanStack Query → durable REST server state
AI SDK useChat → active AI stream state
AI Elements → view primitives
```

不同时引入第二套 assistant runtime 去复制 thread/message/composer state。

# 3. 系统总览

![总体架构](diagrams/overall.png){width=82%}

## 3.1 分层职责

- **Product UI — React + Product Components**：产品页面、业务交互。
- **AI UI Primitives — AI Elements + shadcn/ui**：Message、Reasoning、Tool、Sources、Composer 等表现层。
- **AI UI Runtime — Vercel AI SDK UI**：`useChat`、UIMessage、transport、stream protocol。
- **Product API — FastAPI**：Auth、REST/SSE、业务 lifecycle。
- **Product Runtime — FastAPI modules/services**：Conversation、RequestRun、幂等、限额、cancel、持久化。
- **Agent Port — `AgentExecutor`**：Product 与 Agent 的 framework-neutral contract。
- **Agent Runtime — PydanticAI**：Agent execution、tools、MCP、structured output。
- **Harness — Pydantic AI Harness**：Skills、Planning、Subagents 等高级 capability。
- **Model Gateway — LiteLLM**：Provider abstraction、routing、fallback、gateway auth、cost。
- **Business DB — PostgreSQL**：业务事实 SOT。
- **Coordination — Redis**：rate/quota/concurrency/cancel，未来 stream replay。
- **Durable Execution — DBOS（未来）**：Agent execution crash/restart durability。

# 5. FastAPI Product Runtime

## 5.1 定位

FastAPI 是唯一 Product Runtime / Business Control Plane。

它不是简单代理 PydanticAI 的 HTTP 壳，而是掌握一次产品请求完整生命周期。

## 5.2 核心模块

```text
backend/app/
├ core/
├ modules/
│  ├ auth/
│  ├ user/
│  ├ conversation/
│  ├ request_run/
│  ├ chat/
│  └ usage/                 # M7
├ agent/
│  ├ executor.py            # PydanticAI implementation
│  ├ factory.py
│  ├ deps.py
│  ├ models.py
│  ├ context/
│  ├ capabilities/
│  ├ tools/
│  └ subagents/
└ infra/
   ├ database.py
   ├ redis.py
   └ ...
```

其中 framework-neutral port 推荐保留在 Product side：

```text
backend/app/modules/chat/executor.py
```

实现放：

```text
backend/app/agent/executor.py
```

## 5.3 AgentExecutor Contract

Product side 必须把 Agent 输入构造成 framework-neutral request；PydanticAIExecutor 不直接查询 Product Conversation/Message repository。

推荐 contract：

```python
from dataclasses import dataclass
from datetime import datetime
from typing import Literal, Protocol
from uuid import UUID

@dataclass(frozen=True, slots=True)
class AgentMessage:
    role: Literal["user", "assistant"]
    content: str

@dataclass(frozen=True, slots=True)
class AgentExecutionRequest:
    request_id: UUID
    conversation_id: UUID
    message: str
    history: tuple[AgentMessage, ...]
    deadline_at: datetime

@dataclass(frozen=True, slots=True)
class AgentExecutionResult:
    content: str

class AgentExecutor(Protocol):
    async def execute(
        self,
        request: AgentExecutionRequest,
    ) -> AgentExecutionResult:
        ...
```

关键规则：

```text
ChatService / Product Context Builder
→ ownership check
→ 从 PostgreSQL 读取 server-authoritative durable history
→ 转换为 AgentExecutionRequest.history
→ AgentExecutor
```

禁止：

```text
PydanticAIExecutor
→ 通过 conversation_id 反向查询 Product repository
```

以后可新增 framework-neutral events / usage / cancellation handle，但 Product port 不直接暴露 PydanticAI 类型。

## 5.4 ChatService 的职责

ChatService / ChatOrchestrator 必须保留：

```text
conversation ownership
server-authoritative history loading / projection
idempotency replay
RequestRun creation
user message durable write
admission (rate/quota/concurrency)
absolute deadline
explicit cancellation race
assistant final durable write
terminal transition
Product Error mapping
```

不得拥有：

```text
PydanticAI tool implementation
provider SDK exception details
Harness internal state
model provider key
```

依赖方向必须是：

```text
Product repository/services
        ↓
ChatService
        ↓
AgentExecutionRequest
        ↓
AgentExecutor
```

Agent implementation 不得反向依赖 Product repository 来补齐业务上下文。

# 6. Product Request Lifecycle

![请求生命周期](diagrams/lifecycle.png){width=78%}

## 6.1 Start Transaction

Agent 执行前必须先完成：

```text
BEGIN
1. ownership check
2. idempotency check / insert RequestRun(running)
3. insert user Message
4. update Conversation.last_message_at
COMMIT
```

只有 COMMIT 成功后才允许产生 Agent/LLM 成本。

## 6.2 Agent Execution

M3 非流式阶段可以由 Product request 协程直接等待 AgentExecutor：

```text
Product Runtime
→ AgentExecutor
→ PydanticAIExecutor
→ PydanticAI
→ LiteLLM
```

M8 Production Streaming 引入 in-process `ExecutionSupervisor`，让 execution ownership 与当前 HTTP subscriber 解耦：

```text
Product Start TX COMMIT
        ↓
ExecutionSupervisor.start(request_id, ...)
        ↓
AgentExecutor
        ↓
PydanticAIExecutor
```

`ExecutionSupervisor` 当前只保证同进程内：

```text
request_id → task ownership
deadline supervision
explicit cancellation propagation
graceful shutdown bookkeeping
terminal callback
```

它**不是 durable execution engine**：FastAPI 进程崩溃/服务器重启仍可能丢失正在执行的 task，后续由 DBOS 等解决。

任何 Product transaction 都不得跨越几十秒 Agent execution。

## 6.3 Success Transaction

Agent 产生 final candidate 后，不能立刻向浏览器宣告 Product completed。

```text
BEGIN
1. insert assistant final
2. conditional RequestRun running → completed
3. update Conversation.last_message_at
COMMIT
```

只有 COMMIT 成功后：

```text
Product Runtime
→ authorize terminal event
→ append finish/completed to Redis Stream
→ subscriber/UI observe completion
```

因此 Product completed 的定义是 durable business commit 成功，而不是：

```text
模型生成最后一个 token
PydanticAI run 返回
Vercel adapter 自己产生 finish
```

Streaming 层必须存在 **Terminal Event Gate**：普通 text/tool/source/data event 可实时投影；`finish/error/abort` 等 Product terminal event 只能由 Product lifecycle 授权。

## 6.4 Failure

Agent/LLM/Tool 错误转换为 Product Error Code，然后：

```text
running → failed
finished_at = now
error_code = PRODUCT_CODE
```

不把 provider raw error、key、stack trace 写到 Product error 字段。

## 6.5 Cancellation

当前 P0 状态保持：

```text
running → cancelled
```

语义固定为：

> `cancelled` 表示 Product Request 已经取消，任何晚到 Agent final 都不再有资格写入 assistant final / completed；它不保证 Python coroutine 在同一瞬间已经物理停止。

推荐顺序：

```text
POST cancel
→ ownership check
→ CAS RequestRun running → cancelled
→ publish Redis / CancellationToken signal
→ Agent task stops/unwinds
→ emit Product abort/cancel terminal projection
```

`cancel vs final` 由数据库 conditional terminal transition 决定谁赢：

```text
谁先成功把 running 改成 terminal，谁拥有最终业务结果。
```

未来如果真实产品需要准确展示“已请求停止但尚未确认停止”，再单独扩展：

```text
running → cancelling → cancelled
```

本次 Framework Migration 不顺便扩大状态机。

# 8. Redis 设计

## 8.1 当前职责

保留现有：

```text
IP rate limit
user rate limit
daily quota
user concurrency lease
explicit cancellation coordination
```

Redis 是快速分布式保护层；PostgreSQL 唯一约束继续承担最终 correctness。

## 8.2 M8 增加 Redis Streams

目标：

```text
PydanticAI events
→ Vercel AI event transform
→ Product Stream Projector
→ Terminal Event Gate
→ Redis Stream:{request_id}
→ SSE subscriber(s)
```

事件 stream 解决：

```text
subscriber disconnect
reconnect
cursor replay
multiple subscribers
API replica handoff
```

但不解决：

```text
Agent Python 进程 crash recovery
server restart execution recovery
Business Message durability
```

第一版直接使用 `request_id` 作为 stream identity，不额外创造 `stream_id`。Redis event ID 作为 replay cursor。

Redis Stream 不成为 Business Message SOT。

## 8.3 Key Namespace

建议继续统一：

```text
{prefix}:chat:rate:...
{prefix}:chat:quota:...
{prefix}:chat:concurrency:...
{prefix}:chat:cancel:{request_id}
{prefix}:chat:stream:{request_id}
```

并规定 TTL / retention policy。

第一版 retention：

```text
run 运行中  → 保留完整当前 replay window
terminal 后 → 短期 TTL（例如 24h，最终值由容量测试决定）
```

partial streaming output 只属于 replay/event data，不自动升级为 durable assistant Message。

# 9. PydanticAI Agent Runtime

## 9.1 Core 职责

PydanticAI Core 负责：

```text
Agent loop
model interface / request-response abstraction
Tools / Toolsets
MCP
Dependencies
Structured outputs
Capabilities / Hooks
stream events
```

这里的 model abstraction 是 Agent 侧调用接口；生产 provider routing、credentials、fallback、gateway policy 仍由 LiteLLM 负责。

PydanticAI 官方提供 Vercel AI UI event adapter，可把 Agent run 输入/事件转换为 AI SDK UI stream，并支持 FastAPI/Starlette endpoint 集成。Production 只使用其高级 transform/encode 能力接入 Product lifecycle，不让 adapter 直接成为 Product Runtime。

## 9.2 Harness

Harness 使用方式：

```text
Agent(capabilities=[...])
```

优先 capability：

```text
Skills
Planning
Subagents
Compaction
Tool Output Limits
Guardrails
FileSystem / Shell（有明确需求后）
```

### Harness Stability Rule

Harness 仍采用 0.x versioning，minor release 允许 breaking change。因此：

```text
必须 pin exact/compatible version
必须隔离在 backend/app/agent/capabilities
Product modules 不直接 import harness
升级必须经过 contract tests
```

## 9.3 RuntimeClock

保留 framework-neutral semantic：

```python
runtime_clock_context(...)
```

删除 LangChain middleware wrapper。

未来通过 PydanticAI instructions/capability 注入当前日期、时间、时区。

## 9.4 Client History Trust Boundary

Vercel AI / `useChat` request messages 是 client-controlled。

因此生产架构规定：

```text
客户端提交的 history 不是 Product SOT
```

FastAPI 必须：

```text
conversation_id + current_user
→ ownership check
→ PostgreSQL durable history
→ framework-neutral AgentMessage[]
→ AgentExecutionRequest
```

PydanticAIExecutor 只消费 Product Runtime 已经构造好的 authoritative history，不反向读取 Product Conversation/Message repository。

System instructions 只由服务器拥有；客户端不得通过伪造 system message 修改。

## 9.5 Agent Memory / Step Persistence

Pydantic AI Harness 提供 Step Persistence/Memory 等能力，但它们只能作为 Agent execution/context capability。

若未来启用：

```text
Product Conversation / Message 仍然是业务历史 SOT
```

## 11.4 M8B - Production Streaming

生产链路：

```text
Browser / useProductChat
        ↓
POST /api/v1/chat
        ↓
Auth / AuthZ / Admission / Idempotency
        ↓
Product Start TX
RequestRun(running) + User Message + COMMIT
        ↓
request_id
        ↓
ExecutionSupervisor (in-process, non-durable)
        ↓
AgentExecutionRequest(server-authoritative history)
        ↓
AgentExecutor → PydanticAIExecutor → PydanticAI
        ↓
PydanticAI events
        ↓
VercelAIAdapter transform
        ↓
Product Stream Projector
        ↓
Terminal Event Gate
        ↓
Redis Stream:{request_id}
        ↓
GET /requests/{request_id}/stream?cursor=...
        ↓
SSE / Vercel UI chunks
        ↓
useChat
```

普通非 terminal event：

```text
text / tool / source / data
→ 可实时 append Redis
```

Terminal event：

```text
Agent final candidate
→ Product Success TX
→ assistant final + RequestRun(completed)
→ COMMIT
→ emit finish/completed
```

错误/取消同理，Product terminal state 先获得业务权威，再投影 terminal UI event。

## 11.5 ExecutionSupervisor

M8 引入一个很薄的 in-process execution owner：

```text
ExecutionSupervisor
├ request_id → asyncio Task
├ deadline supervision
├ cancellation handle / token
├ graceful shutdown bookkeeping
└ terminal callback
```

它解决：

```text
HTTP subscriber 断开但 execution 继续
一个 request_id 有明确 task owner
Product cancel 能找到并通知 execution
```

它不保证：

```text
FastAPI process crash 后恢复
服务器重启后恢复
task 自动迁移到其他 replica
```

这些是未来 DBOS/durable execution 的职责。

## 11.6 Reconnect / Replay

推荐：

```text
GET /api/v1/chat/requests/{request_id}/stream?cursor=<redis-event-id>
```

或通过 AI SDK transport 的 `prepareReconnectToStreamRequest` 对齐等价 endpoint。

`ProductChatTransport` 封装 request_id、cursor、auth，业务组件不感知底层 Redis。

多个 FastAPI replica 只需要共享 PostgreSQL + Redis；subscriber 可以连接到与 Agent execution 不同的 replica。

## 11.7 Stop：Product Stop != `useChat.stop()`

AI SDK client `stop()` 本质上 abort 当前浏览器 fetch；PydanticAI 服务端把这种 client disconnect 视为 external cancellation，而不是 Product first-party cancellation。

同时 AI SDK 当前 resumable streams 与 client abort/stop 存在兼容限制。

因此 v8 Product Stop 定义为：

```text
User clicks Stop
→ useProductChat 调 Product Cancel API
→ POST /requests/{request_id}/cancel
→ ownership check
→ CAS running → cancelled
→ CancellationToken / task signal
→ Agent unwind
→ Product abort/cancel terminal event
→ UI reconcile
```

`useProductChat.stop()` 不得简单等价于 AI SDK 原生 `stop()`；需要保持 subscriber 连通以接收 first-party abort/terminal projection，具体客户端 transport 行为由 M8 contract test 冻结。

## 11.8 Partial Output Policy

第一版规定：

```text
completed
→ assistant final 写 PostgreSQL

failed / cancelled
→ partial assistant output 只保存在 Redis replay window
→ 不写 durable Message
```

因此 Redis TTL 到期后，历史页只恢复 durable user message + RequestRun failed/cancelled 状态，不把半截输出冒充正式 assistant final。

若未来产品明确要求永久保存 partial output，再单独设计 output snapshot/message status，不在 M8 偷渡修改 Message contract。

# 13. Deadline / Retry / Cost Boundary

## 13.1 Absolute Deadline

Product Runtime 计算一次绝对 deadline：

```text
started_at + REQUEST_DEADLINE_SECONDS
```

所有下游只消费 remaining budget：

```text
Agent loop
model calls
tools
subagents
```

不能每层重新获得完整 60 秒。

## 13.2 Retry Ownership

```text
LiteLLM       → provider/deployment bounded retry/fallback
Agent         → semantic/tool retry（受 Product budget 限制）
Product       → 不透明失败后的业务 retry/idempotency
```

每层 retry 不能叠加成无限成本。

## 13.3 Cost Attribution

M7 后：

```text
request_id
→ one/many LiteLLM call ids
→ usage rows
→ user/conversation/agent_role
```

Product billing 以 business usage 为准，LiteLLM 数据作为 gateway evidence，不直接取代业务账本。

# 18. Future DBOS Boundary

DBOS 不进入当前 clean baseline，也不进入 M8 第一版。

它未来只解决：

```text
execution durable workflow
crash/restart recovery
long-running steps
worker handoff
```

演进关系：

```text
M8 In-process ExecutionSupervisor
        ↓ implementation evolution
DBOS-backed Durable Execution Supervisor / Workflow
```

Product-facing contract 尽量不变：

```text
RequestRun
AgentExecutionRequest
AgentExecutor
Product terminal callback
```

DBOS 不能替代：

```text
PostgreSQL Product DB
Redis Stream UI replay
RequestRun business lifecycle
```

引入 gate：

1. 已经有真实 restart-loss 问题。
2. Agent execution 与 HTTP subscriber 已解耦。
3. 请求时长/worker isolation 产生运维收益。
4. 用 failure drill 证明收益大于复杂度。

# 22. Hard Gates / Architecture Fitness Functions

每次重大修改必须回答：

## Gate 1 - Framework Replaceability

如果明天把 PydanticAI 换掉，是否需要修改：

```text
Conversation model?
RequestRun model?
Auth?
Billing?
Product API semantics?
```

若需要，说明 framework 泄漏进入 Product Runtime。

## Gate 2 - Business SOT

任何关键产品事实都必须能只看 Product DB 解释：

```text
用户发了什么？
请求是否完成？
是否取消？
最终回答是什么？
成本归属给谁？
```

不能要求读取 Agent checkpoint 才能回答。

## Gate 3 - Disconnect

网络断开后：

```text
Product Request identity 仍存在
Durable state 可查询
明确 Stop 才取消
```

## Gate 4 - No Duplicate Runtime

不得同时出现两套：

```text
Product run state machine
Agent framework run state machine 作为产品 SOT
```

## Gate 5 - Protocol Boundary

Browser 只消费 UI protocol/Product API，不认识 provider/Pydantic internal event schema。

```text
PydanticAI event
→ Vercel transform
→ Product projector
→ stable browser protocol
```

PydanticAI/AI SDK 升级必须通过 protocol contract test。


## Gate 6 - Terminal Event Authority

任何 UI `finish/completed/abort/error` 产品终态都必须满足：

```text
Product terminal state durable/authoritative
→ then emit terminal UI event
```

特别是 completed：assistant final + RequestRun completed 必须已经 COMMIT。

## Gate 7 - Execution Ownership

HTTP subscriber 与 execution 解耦以后，必须能回答：

```text
谁拥有 request_id 对应的 task？
谁负责 deadline？
谁接受 cancel signal？
进程 shutdown 怎么处理？
进程 crash 后是否可恢复？
```

M8 的答案是 `ExecutionSupervisor`，且明确 **non-durable**；未来才由 DBOS 等升级 durability。

## Gate 8 - Stop / Resume Semantics

Product Stop 不等于 browser fetch abort。

必须 contract-test：

```text
first-party cancel → Product terminal cancel/abort projection
network disconnect → execution 默认继续
reconnect → Redis replay/live
client abort/resume SDK limitation 不侵入 Product lifecycle
```

```text
❌ HTTP disconnect == Product cancel
❌ Redis Stream == Business Message SOT
❌ Agent checkpoint == Product History SOT
❌ DBOS == UI stream replay
❌ FastAPI → Hono → PydanticAI 无收益多一跳
❌ React 同时维护 AI SDK + 第二套 agent UI runtime
❌ Product Stop 直接等价 useChat.stop()/browser abort
❌ PydanticAIExecutor 反向查询 Product Conversation repository
❌ Agent/Vercel finish 先于 Product COMMIT 对外宣告完成
❌ 前端直连 LiteLLM / provider
❌ 一次 migration 同时做 Framework Migration + RequestRun 状态机大改 + Streaming
```

# 24. 技术决策摘要（ADR Index）

## ADR-A01 Product Runtime

**Accepted：FastAPI modular monolith**  
理由：业务状态、数据库和 Agent 都在 Python/Pydantic 生态；不增加无收益 Node/Hono service boundary。

## ADR-A02 Agent Runtime

**Accepted：PydanticAI behind AgentExecutor**  
理由：Agent framework 回归 execution engine；官方支持 capabilities、MCP、stream events 和 UI adapters。

## ADR-A03 Harness

**Accepted with pinning：Pydantic AI Harness**  
理由：Skills/Planning/Subagents 等能力以 capability 组合；因 0.x 必须本地隔离。

## ADR-A04 Frontend AI Runtime

**Accepted：Vercel AI SDK UI**  
理由：`useChat` + transport + UIMessage protocol；Python/FastAPI custom backend 可兼容。

## ADR-A05 AI Components

**Preferred with Package Gate：AI Elements**  
理由：shadcn-style composable source primitives；不引入第二套 Product/Thread runtime。Vite 兼容性必须实测。

## ADR-A06 Model Gateway

**Accepted：LiteLLM Proxy**  
理由：Provider abstraction、routing/fallback、service key、gateway cost/usage 集中管理。

## ADR-A07 Durability

```text
PostgreSQL = Business
Redis Streams = UI stream replay
DBOS future = Execution
```

三者不可混用。

---


## ADR-A08 Execution Supervision

**Accepted：M8 使用 in-process ExecutionSupervisor，未来可演进为 DBOS-backed durable execution。**  
理由：先把 HTTP subscriber 与 Agent execution ownership 解耦，但不提前支付分布式 workflow 成本。

## ADR-A09 Terminal Event Gate

**Accepted：Product Runtime 拥有 terminal event authority。**  
理由：Agent completion 不是 Product completion；completed 只有在 assistant final + RequestRun terminal COMMIT 后才能对 UI 可见。

## ADR-A10 History Boundary

**Accepted：Product Runtime 构造 server-authoritative AgentExecutionRequest.history。**  
理由：Agent implementation 不反向读取 Product repository，保证 Product → Agent 单向依赖。

# 26. 最终结论

v8 的最终形态不是“选择了哪个 Agent Framework”这么简单。

真正的架构是：

```text
Product Runtime = Control Plane
Agent Runtime   = Execution Engine
UI Runtime      = Presentation/Transport State
Infrastructure  = Durability/Coordination
```

当前最优实现：

```text
React + Vite
  ↓
AI Elements + shadcn/ui
  ↓
Vercel AI SDK UI
  ↓
FastAPI Product Runtime
  ↓
ExecutionSupervisor (M8, in-process)
  ↓
AgentExecutor
  ↓
PydanticAI + Harness
  ↓
LiteLLM

PostgreSQL = Product SOT
Redis      = Coordination + Stream Replay
Terminal Gate = Product lifecycle-authorized UI terminal events
DBOS       = Future Execution Durability
```

**分的是 ownership，不是机器。**  
**Product Runtime 必须唯一。**  
**Agent Framework 必须可替换。**  
**先模块化单体，出现真实运维收益后再拆 Agent Worker。**
