## 0. 执行摘要

本架构的核心决策仍然只有一句话：

> **Product Runtime 与 Agent Runtime 在逻辑 ownership 上彻底分离，但当前物理部署保持同进程/同容器的模块化单体；Product Runtime 是唯一业务控制面，PydanticAI 只是可替换的 Agent execution engine。**

v8.2 在 v8.1 的基础上完成一个重要收敛：**不再把 Redis Streams / XADD / XREAD 固定为 UI stream replay 的默认架构。** 仓库已经落地 framework-neutral `StreamResumeStore` port 和 `RedisStreamResumeStore` 实现，其职责仅为 active HTTP/UI stream resumption：单 producer claim、跨 replica Redis Pub/Sub discovery、producer-memory replay、opaque SSE chunk reconnect。它不拥有 Product RequestRun、不拥有业务历史、不拥有 Product Cancel，也不提供 process-crash execution durability。

### 0.1 最终技术栈


### 0.3 v8.2 相对 v8.1 的关键变化

```text
Redis Streams 固定方案
        ↓ SUPERSEDED
StreamResumeStore contract
        ↓
RedisStreamResumeStore implementation
```

同时冻结以下规则：

1. `stream_id = str(request_id)`，不增加 Product `stream_id` 字段。
2. Redis Stream/XADD/XREAD/cursor 不再是 Product/browser contract。
3. Stream state `MISSING/ACTIVE/DONE/FAILED/INTERRUPTED` 只是 transport state，绝不能替代 RequestRun。
4. Browser disconnect 只应 detach subscriber；不能取消 Product Request。
5. Product Stop 继续走独立 cancel API + Product CAS + PydanticAI first-party cancellation。
6. success terminal UI event 必须晚于 assistant final + RequestRun completed 的 PostgreSQL COMMIT。
7. producer process crash 仍不属于 active stream resume 能解决的范围；这是未来 DBOS/Temporal 的 execution durability 问题。
8. AI SDK native `resume:true` 与 browser abort/stop 的当前兼容限制必须通过 M8 custom transport E2E Gate，不允许直接假定开关即可生产使用。

# 2. 第一性原理与核心架构原则

## 2.1 Single Product Runtime

系统只能有一套业务运行语义。

Product Runtime 拥有：

```text
User / Auth / AuthZ
Conversation
Message
RequestRun
Idempotency
Rate Limit
Quota
Concurrency
Deadline
Explicit Cancellation
Usage Attribution
Billing
Audit
Retention / Delete Policy
```

任何 Agent Framework 都不得成为这些概念的 SOT。

## 2.2 Agent Runtime 是 Execution Engine，不是 Product Platform

PydanticAI 拥有：

```text
Agent loop
Model calls
Tools / Toolsets
MCP
Structured output
Dependencies
Capabilities / Hooks
Skills
Planning
Subagents
Agent-local context management
```

它不拥有：

```text
用户套餐
Conversation ownership
RequestRun 状态
业务幂等
业务计费
业务历史 SOT
产品 cancel 权限
```

## 2.3 逻辑分离，物理先不分

当前阶段采用：

```text
Modular Monolith

FastAPI process/container
├ Product Runtime
├ AgentExecutor port
└ PydanticAI implementation
```

而不是现在就：

```text
FastAPI Product API
    ↓ RPC
Agent Microservice
```

只有出现独立 autoscaling、长任务、sandbox、GPU、故障隔离、独立发布周期等明确需求时，才物理拆分 Agent Worker。

## 2.4 Business Durability、Active Stream Resume、Execution Durability 三分

```text
Business durability      → PostgreSQL
Active UI stream resume  → StreamResumeStore + Redis coordination
Execution durability     → DBOS / Temporal 等（未来）
```

这里刻意不再使用“Stream Durability = Redis Streams”的表述。当前 `StreamResumeStore` 只保证 producer 仍存活时的 active stream reconnect/replay；producer-memory buffer 并不是 durable execution log。

三类能力分别回答：

```text
业务最终事实是什么？             PostgreSQL
浏览器掉线后如何重新附着当前流？ StreamResumeStore
Python execution 进程挂了怎么办？ Future DBOS/Temporal
```

它们不能由一个 checkpoint 或 Redis stream 概念混在一起。
## 2.5 Transport Disconnect != Product Cancel

浏览器刷新、网络断开、SSE 断开，只结束 subscriber；不得天然等价于终止 Product Request。

真正的 Stop：

```text
POST cancel
→ ownership check
→ Product Request terminal/cancel signal
→ Agent cancellation token/task cancellation
```

## 2.6 Product DB 禁止出现 Agent Framework Identity

禁止：

```text
langgraph_thread_id
pydantic_thread_id
agent_thread_id
framework_run_id
```

Product identity 固定为：

```text
conversation.id
request_run.id == request_id
```

如未来 execution engine 需要额外执行 ID，只能作为可替换 infrastructure mapping，并优先挂在 RequestRun execution metadata，而不是污染 Conversation。

## 2.7 Frontend 同样只能有一套 Active AI Runtime

采用：

```text
TanStack Query → durable REST server state
AI SDK useChat → active AI stream state
AI Elements → view primitives
```

不同时引入第二套 assistant runtime 去复制 thread/message/composer state。

## 3.2 Streaming Sidecar-in-Process 逻辑

Streaming 不建立第二 Product Runtime：

```text
PydanticAI event stream
    ↓
VercelAIAdapter transform / encode
    ↓
Lifecycle-aware Terminal Gate
    ↓
StreamResumeStore<opaque SSE string>
    ↓
RedisStreamResumeStore
    ├ atomic producer claim
    ├ Redis state/KV
    ├ Redis Pub/Sub request/listener discovery
    └ producer-memory replay buffer
    ↓
FastAPI StreamingResponse / reconnect subscriber
    ↓
AI SDK UI
```

## 3.3 分层职责

- **Product UI**：产品页面和业务交互。
- **AI UI Primitives**：Message、Reasoning、Tool、Sources、Composer 等表现层。
- **AI UI Runtime**：`useChat`、UIMessage、ChatTransport、stream parsing；不成为业务 SOT。
- **Product API / Runtime**：Auth、REST/SSE、业务 lifecycle、business persistence。
- **ExecutionSupervisor**：当前进程内 request task owner；不是业务状态机。
- **Agent Port**：Product → Agent 的 framework-neutral contract。
- **PydanticAI**：execution engine。
- **Harness**：Skills、Planning、Subagents 等 capability。
- **LiteLLM**：production model gateway。
- **PostgreSQL**：唯一 Product durability。
- **Redis**：分布式 coordination；不成为 Business Message SOT。
- **StreamResumeStore**：只负责 active UI transport reconnect/replay。
- **DBOS（未来）**：当 crash/restart recovery 成为真实需求时负责 durable execution。

## 3.4 最重要的 ownership 口诀

> **分的是 ownership，不是机器。**

当前可以全部在同一个 FastAPI deployment 中；只要代码依赖方向不反转，未来物理拆 Agent Worker、替换 PydanticAI、替换 stream backend 都不需要改 Product schema。

# 5. FastAPI Product Runtime

## 5.1 定位

FastAPI 是唯一 Product Runtime / Business Control Plane。它不是简单代理 PydanticAI 的 HTTP 壳，而是掌握一次 Product Request 从 admission 到 durable terminal 的完整生命周期。

## 5.2 当前代码模块

当前仓库真实结构已经包含：

```text
backend/app/
├ agent/
│  └ executor.py              # 当前 framework-neutral AgentExecutor port
├ infra/
│  ├ redis.py
│  └ stream_resume/           # 已落地
├ modules/
│  ├ conversation/
│  ├ request_run/
│  └ chat/
│     ├ api.py
│     ├ runtime.py            # rate/quota/concurrency/cancel
│     ├ schema.py
│     └ service.py            # Product lifecycle
└ ...
```

v8.2 不为了“目录看起来更纯”立即搬动 `app/agent/executor.py`。规则改为：

```text
app/agent/executor.py
= 只允许 framework-neutral port / DTO / Product-safe errors
= 禁止 import pydantic_ai

app/agent/pydantic_executor.py   # M3 新增
= PydanticAIExecutor implementation
= 可以 import pydantic_ai
```

这样避免一次无收益路径 churn，同时保持实际依赖边界。

## 5.3 AgentExecutor Target Contract

当前代码已采用以下 server-authoritative input DTO；Product durable history 由 ChatService 投影，PydanticAIExecutor 不反向查询 Product repository：

```python
from dataclasses import dataclass
from datetime import datetime
from typing import Literal, Protocol
from uuid import UUID

@dataclass(frozen=True, slots=True)
class AgentMessage:
    role: Literal["user", "assistant"]
    content: str

@dataclass(frozen=True, slots=True)
class AgentExecutionRequest:
    request_id: UUID
    conversation_id: UUID
    message: str
    history: tuple[AgentMessage, ...]
    deadline_at: datetime

@dataclass(frozen=True, slots=True)
class AgentExecutionResult:
    content: str

class AgentExecutor(Protocol):
    async def execute(
        self,
        request: AgentExecutionRequest,
    ) -> AgentExecutionResult:
        ...
```

权威流向：

```text
PostgreSQL durable Messages
        ↓
ChatService / Product History Projector
        ↓
AgentExecutionRequest.history
        ↓
AgentExecutor
        ↓
PydanticAIExecutor
```

禁止：

```text
PydanticAIExecutor
→ conversation_id
→ Product ConversationRepository
```

Agent implementation 不得反向读取 Product DB 来“补齐上下文”。

## 5.4 ChatService Ownership

保留当前已落地能力：

```text
conversation ownership
idempotency replay
RequestRun start
user message durable write
rate/quota/concurrency admission
absolute deadline
explicit cancellation race
assistant final durable write
terminal transition
Product Error mapping
```

M3/M8 新增：

```text
server-authoritative history projection
ExecutionSupervisor handoff
stream lifecycle callbacks
Terminal Event Gate authorization
reconcile after transport failure
```

不得拥有：

```text
PydanticAI tool internals
provider SDK raw exception
Harness internal state
provider keys
transport backend implementation detail
```

## 5.5 disconnect 语义（Step 6 已硬化）

Step 6 已移除 `ChatService._execute_agent()` 的 `disconnect_checker` 分支，并由
`ExecutionSupervisor` 拥有 Agent/adapter task。HTTP subscriber 生命周期不再进入
Product execution 的 cancellation race：

```text
HTTP subscriber disconnect
→ detach subscriber only
→ Product Request remains RUNNING
→ ExecutionSupervisor owns task
→ StreamResumeStore keeps active stream attachable
```

只有明确 Product Cancel API 才可以竞争 `running → cancelled`。

# 6. Product Request Lifecycle

## 6.1 Start Transaction

Agent 执行前必须先完成：

```text
BEGIN
1. conversation ownership check
2. idempotency check / insert RequestRun(RUNNING)
3. insert user Message
4. update Conversation.last_message_at
COMMIT
```

只有 Product Start TX COMMIT 成功，才能产生 Agent/LLM cost。

当前代码已经遵循这个基本结构。

## 6.2 Authoritative History Projection

Start TX 后、Agent execution 前：

```text
conversation_id + current user
→ load durable Product Messages
→ project allowed user/assistant history
→ build AgentExecutionRequest
```

Client `UIMessage[]` 可以携带 UI intent、tool approval 等协议数据，但不能替代 Product durable history 的真实性判断。

## 6.3 M3 非流式 Execution

PydanticAI 刚接入时允许先保持：

```text
ChatService
→ AgentExecutor
→ PydanticAIExecutor
→ final content
→ Success TX
```

该阶段不要求先把 streaming/resume 一次做完，避免 Framework Migration 和 Streaming 同时爆炸。

## 6.4 M8 Streaming Execution Ownership

M8 引入 `ExecutionSupervisor`：

```text
Product Start TX COMMIT
        ↓
ExecutionSupervisor.start(request_id, execution coroutine)
        ↓
AgentExecutor
        ↓
PydanticAIExecutor
```

职责：

```text
strong task registry: request_id → asyncio.Task
absolute deadline supervision
Product cancellation handle/token
subscriber-independent execution lifetime
graceful shutdown bookkeeping
terminal callback
```

明确不负责：

```text
PostgreSQL RequestRun SOT
business idempotency
durable crash recovery
cross-process task migration
```

## 6.5 Non-terminal Streaming

Agent execution 可以实时产生：

```text
text
tool input/output
source
data
reasoning status（只允许可公开内容）
metadata
```

经 PydanticAI Vercel adapter 编码后进入 lifecycle-aware stream gate。非 terminal chunk 可立即送入 `StreamResumeStore`。

## 6.6 Success Transaction 与 Terminal Gate

Agent final 只是 **candidate**：

```text
Agent final candidate
        ↓
BEGIN
1. insert assistant final Message
2. CAS RequestRun RUNNING → COMPLETED
3. update Conversation.last_message_at
COMMIT
        ↓
Product Runtime authorizes success terminal event
        ↓
finish/completed SSE chunk
```

因此 Product completed 的定义永远不是：

```text
最后一个模型 token 已生成
PydanticAI run 返回
Vercel adapter 自己产生 finish
```

而是：

> **assistant final + RequestRun completed 已经 durable COMMIT。**

如果 Product COMMIT 成功但最后的 transport terminal emit 失败：

```text
PostgreSQL remains SOT
→ 不回滚已提交业务事务
→ reconnect/status endpoint 依据 durable Product state reconcile
→ 必要时 synthetic final UI state
```

## 6.7 Failure

Agent/LLM/Tool error 映射 Product Error Code：

```text
RUNNING → FAILED
finished_at = now
error_code = Product-safe code
```

Transport 可发 error terminal projection，但 Product failure 必须先获得业务权威。

## 6.8 Cancellation

P0 状态仍为：

```text
RUNNING → CANCELLED
```

语义：

> `CANCELLED` 表示 Product cancellation 赢得 terminal CAS，任何晚到 Agent final 都不再具有 commit eligibility；不表示 underlying coroutine 在同一 CPU tick 已物理停止。

顺序：

```text
POST /requests/{request_id}/cancel
→ AuthZ / ownership
→ CAS RUNNING → CANCELLED
→ Redis Product cancel coordination
→ PydanticAI CancellationToken / supervisor cancellation signal
→ Agent unwind
→ Product abort/cancel UI projection
```

`cancel vs final`：谁先成功完成 Product terminal CAS，谁赢。晚到 final 必须丢弃。

## 6.9 Disconnect

v8.2 的最终语义：

```text
Browser F5 / network drop / SSE disconnect
→ subscriber gone
→ execution continues
→ StreamResumeStore retains producer-memory backlog while producer process lives
→ reconnect can attach again
```

它**不得**自动触发 RequestRun cancelled。

## 6.10 Partial Output Policy

```text
COMPLETED
→ durable assistant final in PostgreSQL

FAILED / CANCELLED
→ partial UI output transport-only
→ not Product Message
```

如果未来需要永久保留 partial answer，应新增明确的 message status/output snapshot 设计，不能把半截内容偷偷当 final assistant Message。

## 7.2 Conversation

```text

```


## 7.3 Message

```text

role
content
reasoning_summary (nullable; assistant-only public display projection)
reasoning_duration_ms (nullable; measured public reasoning intervals only)

updated_at
```

P0 durable message 只保存：

```text
user
assistant final
```

`reasoning_summary` 只允许保存已经通过 UI adapter 公开展示的文本投影；
`reasoning_duration_ms` 只累计 `reasoning-start → reasoning-end` 的公开流片段，不得用
RequestRun 总耗时冒充思考时间。两者都不进入 authoritative Agent history，也不得保存
provider signature / details。不得把 tool
scratchpad、system prompt、private reasoning、subagent internal message 当作 Product
Message。

Streaming delta 不逐条写 message 表。

```text

conversation_id
idempotency_key
status
started_at
deadline_at
finished_at
error_code
created_at
updated_at
```

关键 invariant：

```text
UNIQUE(user_id, idempotency_key)
UNIQUE running per conversation
terminal status => finished_at IS NOT NULL
```

## 7.5 Business LLM Usage（M7）

建议独立表而不是把 token/cost 塞进 RequestRun：

```text
business_llm_usage
├ id
├ request_id
├ user_id
├ conversation_id
├ litellm_call_id
├ agent_role
├ logical_model
├ actual_model
├ input_tokens
├ output_tokens
├ total_tokens
├ cost
├ status
└ timestamps
```

写入必须幂等，并允许一次 RequestRun 多次模型调用。

字段 provenance 冻结如下：

```text
AgentExecutor success snapshot
→ call_index / logical_model / reported_model / provider_response_id
→ token/cache/audio buckets / successful tool_calls

Product lifecycle enrichment
→ request_id / user_id / conversation_id / agent_role

LiteLLM gateway evidence
→ litellm_call_id / actual model or deployment / authoritative usage / cost / status
```

当前 Step 4 contract 不把 `provider_response_id` 称为 `litellm_call_id`，也不把 PydanticAI `genai-prices` estimate 称为 business cost。`token_usage=None` 表示 provider 未报告；不得改写为零。失败、cancel、deadline 和未来 Subagent 的完整计量必须依赖 shared request recorder + LiteLLM reconciliation，不能只依赖成功时的 `AgentExecutionResult`。

# 8. Redis 与 Active Stream Resume 设计

## 8.1 Redis Product Coordination（已落地）

现有 Redis 继续承担：

```text
IP rate limit
user rate limit
daily quota
user concurrency lease
explicit cancellation coordination
```

`RedisChatRuntime` 是 Product protection/coordination implementation；PostgreSQL unique/CAS 仍承担最终 correctness。

## 8.2 StreamResumeStore Port（已落地）

`backend/app/infra/stream_resume/protocol.py` 定义：

```python
class StreamResumeStore(Protocol):
    async def start(stream_id, producer): ...
    async def resume(stream_id, *, skip_characters=0): ...
    async def start_or_resume(stream_id, producer, *, skip_characters=0): ...
    async def status(stream_id): ...
    async def close(): ...
```

它接收/返回：

```text
AsyncIterator[str]
```

字符串是 opaque encoded chunks；Store 不解析 Vercel/PydanticAI event schema。

## 8.3 Transport State

```text
MISSING      没有 active/known transport
ACTIVE       producer transport owner 仍存活
DONE         transport 正常完成
FAILED       producer/transport 失败
INTERRUPTED  owner shutdown/interruption
```

硬规则：

```text
StreamState != RequestRunStatus
```

例如：

```text
RequestRun = COMPLETED
StreamState = FAILED
```

可能发生在 Product COMMIT 后 terminal SSE emit 出错；此时 PostgreSQL 仍是唯一业务事实源。

## 8.4 RedisStreamResumeStore（✅ Step 1 fencing 已验证）

当前 implementation：

```text
RedisStreamResumeStore
├ injected app Redis client
├ internal Pub/Sub connection
├ atomic active producer claim (SET NX + TTL)
├ Redis KV transport state
├ Redis Pub/Sub resume request / live chunk fanout
├ producer-memory replay buffer
└ resume ack timeout / optional heartbeat
```

它故意**不使用 Redis Streams**作为默认 per-chunk durable log。

核心路径：

```text
Producer process A
├ execution
├ encoded chunks
└ in-memory backlog
       │
       ├→ subscriber A
       │
       └→ Redis Pub/Sub ← resume request from replica B
                            ↓
                       subscriber B
```

因此跨 FastAPI replica resume 的前提是：**原 producer process 仍然活着。**

Step 1 已修复 P0-1：state/lease 分离、per-producer token、Lua 原子 claim/renew/release/state transition；takeover 时旧 Pub/Sub handler 在 ACK/replay 前验证 token ownership；heartbeat lease loss 会与阻塞中的 producer `anext()` 竞争并立即 fence。真实 Redis tests 已覆盖并发 claim、跨 store resume、TTL takeover、旧 owner 不覆盖新 state/lease、terminal retention 与共享 client lifecycle。

## 8.5 Identity

固定：

```text
stream_id = str(request_id)
```

禁止新增：

```text
conversation.stream_id
request_run.stream_id  # 除非未来底层 implementation 真正需要 infrastructure mapping
```

Product identity 继续只有 conversation/request_id。

## 8.6 Redis Lifecycle

`RedisStreamResumeStore(redis_client)` 使用 `app.infra.redis` 已有 client。

```text
Application owns Redis client lifetime
StreamResumeStore owns only its Pub/Sub connection / producer tasks
```

`store.close()` 不得关闭共享 Product Redis client。

## 8.7 Replay Policy

P0 推荐：

```text
F5 reconnect
→ resume(request_id, skip_characters=0)
→ replay 当前 active assistant stream 从起点到 live
```

原因：避免浏览器自己维护额外 cursor SOT，也避免 cursor 与 durable Product history 混合。

只有 M8 E2E/性能测试证明整流 replay 过大，才启用：

```text
skip_characters > 0
```

该值仍是 transport optimization，不进入 Product schema。

## 8.8 能解决与不能解决

能解决：

```text
HTTP subscriber disconnect
browser F5 后重新附着
new subscriber 落到另一个 FastAPI replica
multiple subscriber attach（按实现 contract 验证）
producer仍活着时 backlog + live continuation
```

不能解决：

```text
producer FastAPI process hard crash
server restart 后继续 Agent execution
Python task 跨 replica 自动迁移
Business Message durability
```

这些属于 Execution Durability / Product Durability。

## 8.9 旧 Redis Streams 文档状态

`docs/最小实现Stream Durability.md` 中的以下方案现在只保留为历史研究参考：

```text
XADD per event
XREAD + Redis event-id cursor
Redis Stream:{request_id}
custom run.started/text.delta/tool.* protocol
```

v8.2 明确 **SUPERSEDED** 该默认方案。后续不要依据该文档实现 M8；若未来经 benchmark 证明 Redis Streams 比当前 Pub/Sub model 更合适，也只能作为 `StreamResumeStore` 的另一 implementation，而不是改 Product contract。

## 8.10 Key Namespace

Product coordination 延续：

```text
{prefix}:chat:rate:...
{prefix}:chat:quota:...
{prefix}:chat:concurrency:...
{prefix}:chat:cancel:{request_id}
```

Stream resume implementation 使用独立 namespace，例如：

```text
travel-agent:stream-resume:...
```

具体 key shape 属于 infra private contract，Product module 不直接拼这些 key。

# 9. PydanticAI Agent Runtime

## 9.1 当前状态

当前工作区的 PydanticAI non-streaming executor、authoritative history、LiteLLM logical-model wiring、deadline 与 product-safe error mapping 已通过 Gate A；Vercel adapter 仍只是 streaming prototype，M8 production wiring 尚未完成。

## 9.2 Core Ownership

PydanticAI 负责：

```text
Agent loop
model interface / request-response abstraction
Tools / Toolsets
MCP
Dependencies
Structured outputs
Capabilities / Hooks
stream events
agent-local context
```

它不拥有 Product RequestRun、AuthZ、business history、quota/billing、Product cancellation policy。

## 9.3 Vercel AI Adapter

PydanticAI 官方 Vercel integration 原生支持 AI SDK UI protocol；高级 API 可把 Agent events 转换并编码为 SSE string stream。

Production 使用方式：

```text
Product Runtime
→ AgentExecutionRequest
→ PydanticAIExecutor
→ PydanticAI event stream
→ VercelAIAdapter transform / encode_stream
→ Lifecycle-aware Stream Gate
→ StreamResumeStore
```

`dispatch_request()` 只用于 compatibility spike/example，不直接成为 Production Product endpoint，因为 Product Runtime 必须先做 AuthZ、idempotency、Start TX、server-authoritative history 和 terminal gating。

## 9.4 Protocol Version Gate

PydanticAI adapter 与 AI SDK major 必须成对测试。官方 adapter 存在 `sdk_version` target 概念，因此项目必须 pin：

```text
PydanticAI version
@ai-sdk/react / ai major
VercelAIAdapter sdk_version
protocol contract fixture
```

不能用“都装 latest”替代 compatibility decision。

## 9.5 First-party Cancellation

Product Stop 应映射到 PydanticAI first-party cancellation token/handle：

```text
Product cancel CAS
→ cancellation token
→ PydanticAI run unwind
→ abort projection
```

browser fetch abort/client disconnect 不是 Product first-party cancellation。

## 9.6 Harness

Pydantic AI Harness 作为 capability layer，按真实需求增加：

```text
Skills
Planning
Subagents
Compaction
Tool Output Limits
Guardrails
FileSystem / Shell（有必要后）
```

Product modules 不直接 import Harness types；版本必须 pin，升级必须过 contract/eval。

Harness `Skills` 只加载 `SKILL.md` 的 description/instructions，不读取资源文件，也不自动注册 Tool。项目 capability composition 必须显式维护并校验依赖：

```text
selected Skill
→ required tool names
→ registered PydanticAI Tool/Toolset
→ missing dependency: fail closed at Agent construction
```

底座可在 Gate A 前用“单 deferred Skill + 单确定性本地 Tool”验证；Search、Weather、Maps、Subagents 等外部或多模型调用能力仍需等 usage/deadline/cancel 边界完成后逐项启用。不得暴露一个引用了尚未注册 Tool/Subagent 的完整 Skill。

## 9.7 RuntimeClock

保留 framework-neutral runtime clock semantic，通过 PydanticAI dynamic instructions 注入日期、时间、时区，不再依赖 LangChain middleware。静态 Agent guidance 保持 cache-stable；时间 callable 在每次 Agent run 重新求值，不能在 cached Agent 构造时冻结。

## 9.8 Server-authoritative History

浏览器 messages 不是 Product SOT：

```text
PostgreSQL
→ Product history projection
→ AgentExecutionRequest.history
→ PydanticAI message_history mapping
```

PydanticAI 的 message-history API 是 Agent context mechanism，不是 Product business history database。

## 9.9 Agent Memory / Step Persistence

Harness Memory/Step Persistence 即使启用，也只属于 Agent execution/context capability：

```text
Product Conversation / Message remains SOT
Agent persistence uses separate namespace/storage
```

不得让 Agent memory 决定用户是否拥有 Conversation、请求是否已收费、RequestRun 是否完成。

## 9.10 Travel Planning + Topic Research Architecture

Main Prompt 保持领域无关；Travel Planning 的领域 SOP、Candidate Plan、Research routing、路线质量、Budget / FX 和最终行程规范全部由 `travel-planning` Skill 负责。

当前目标架构固定为：

```text
Domain-neutral Main
→ travel-planning Skill
→ Candidate Plan
→ Reality Gaps
→ Isolated Facts OR Research Topics
   ├─ Main Tools
   └─ research_agent × 0..N
      ├─ independent topics: same-turn parallel tool calls
      └─ dependent topics: staged after Main evaluates prior Findings
→ ResearchFindings / verified facts
→ Main revise Candidate Plan
→ Budget / FX
→ Final Plan
```

职责边界：

- Main 是最终用户意图整合者和最终回答者，但不在全局 instructions 中拥有 Travel Planning SOP；
- `travel-planning` Skill 是 Travel Planning 领域行为 Source of Truth；
- 完整旅行规划先形成 Candidate Plan，再识别会实质影响方案成立的 Reality Gaps；
- 单个、孤立、答案边界清晰的现实事实由 Main 使用 Native Web Search、`web_fetch`、Maps、Weather 核验；
- 多个语义相关 Reality Gaps 组成一个 bounded Research Topic 时，由 Main 委托一次 `research_agent`；
- Main 负责拆 Research Topic，`research_agent` 负责拆 Search / Read / Fetch / Compare / Reason 等 Research Steps；
- 一次 Main run 可以委托 0..N 个 Research Topics，不设置固定 child call-count gate；
- 多个彼此独立 Topic 可以由 Main 在同一个 model turn 发出多个 `research_agent` tool calls，并由 PydanticAI 原生 non-sequential function-tool execution 并发执行；
- 有信息依赖的 Topic 必须分阶段：Research A → Main 判断 → 必要时 Research B；
- `research_agent` 使用 PydanticAI 自身 iterative model → tool → model loop，不额外实现 Research workflow engine；
- `research_agent` 只接收最小 `ResearchRequest`（objective / relevant context / constraints），只返回结构化 `ResearchFindings`；
- child Research execution 处于同一个 Product RequestRun 内，通过直接 await 保持取消传播；
- 每个 child 使用独立 request/tool usage limits 和独立 evidence trace，Product usage 聚合 Main + 所有 Research children；
- Research Agent 的完整内部 tool trajectory 不回灌 Main，只通过 Findings 交接；
- 可恢复的 child provider/output failure 在 capability 边界降级为该 Topic 的 unresolved Findings，不无故取消独立 sibling；父 cancellation 和硬 UsageLimit 继续传播；
- 当前价格、开放、预约、运营、政策等动态事实必须来自真实工具轨迹；unsupported verified claim 必须降级为 unresolved；
- PostgreSQL / Redis / Conversation / Message / RequestRun / Streaming ownership 不因 child Agent 改变。

Research Agent 工具面固定为：

```text
Native Web Search
web_fetch
search_maps
get_weather
```

它不拥有 Budget / FX，也不能递归调用自身或其他 Agent。

本架构不恢复 `DynamicWorkflow`、`research_worker`、固定 research axes 或显式 Python worker fan-out。独立 Topic 的并行来自 PydanticAI 原生 tool execution，而不是新的 Research orchestration runtime。

# 10. LiteLLM Model Gateway

LiteLLM 保持中央模型网关。

## 10.1 Gateway Ownership

```text
Provider API keys
logical model → provider routing
primary / fallback
bounded retry
provider health / cooldown
cost / spend
virtual service key
production provider abstraction
```

FastAPI/PydanticAI 生产环境只拿：

```text
LITELLM_BASE_URL
LITELLM_SERVICE_KEY
LLM_LOGICAL_MODEL
```

Production rule：

```text
PydanticAI model interface
→ LiteLLM logical model
→ provider routing
```

PydanticAI 直连 Provider 只允许 test/dev/spike，不能悄悄绕过 LiteLLM 的 routing、cost 和 credentials policy。

## 10.2 Product Runtime 仍然拥有

```text
user quota
business idempotency
E2E deadline
business attribution
billing policy
```

## 11.1 Protocol SOT


AI SDK protocol 已覆盖 text、tool、source、data、reasoning/message metadata 等 UI parts，并明确允许 Python 等 custom backend 实现兼容 endpoint。因此 v8.2 不维护第二套长期 `text.delta/tool.started/run.completed` 自定义 wire schema。

如果 Product 有自定义数据，使用 AI SDK/PydanticAI 支持的 data/source chunk extension，而不是另起一个 runtime protocol。

## 11.4 M8B - Production Two-plane Model

生产时逻辑拆成两个 plane，**但 POST 直接返回 initial SSE stream**（对齐 `StreamResumeStore.start()` 的 attached-start API 与 AI SDK 官方 resumable 模式；不得用「POST JSON + GET initial stream」——那会留下无人消费的 primary consumer 造成内存泄漏）。

```text
→ server-authoritative history
```

## 11.6 Lifecycle-aware Terminal Event Gate

核心规则：

```text
Non-terminal chunk authority = Agent/Adapter
Terminal Product authority   = Product Runtime
```

非 terminal：

```text
text/tool/source/data/metadata
→ immediate stream allowed
```

三种 Product terminal 都必须先 PostgreSQL COMMIT 再 emit 对应 UI terminal：

```text
SUCCESS terminal：
  Agent finish candidate → HOLD
  → Product Success TX（assistant INSERT + RequestRun completed CAS + COMMIT）
  → RELEASE finish terminal chunk

ABORT terminal：
  CancellationToken → PydanticAI abort candidate → HOLD
  → RequestRun running → cancelled COMMIT
  → RELEASE abort chunk

PRODUCT ERROR terminal：
  PydanticAI/provider exception → Product error mapping → HOLD
  → RequestRun running → failed（error_code）COMMIT
  → RELEASE Product-safe error terminal
```

不变量：

```text
UI terminal state → Product DB 已存在对应 terminal truth
（completed / cancelled / failed 三种都成立，不只 success）
```

## 11.7 StreamResumeStore Integration

M8 不再实现：

```text

Redis Stream cursor
```

而是复用已经落地的：

```text

        ↓
```

producer factory 应大致包围：

```text

→ VercelAIAdapter encoded stream

```

## 11.8 ExecutionSupervisor

```text

├ request_id → task
├ request_id → cancellation handle/token
├ absolute deadline
├ graceful shutdown
```




## 11.9 Reconnect Endpoint

最终 endpoint shape 由 `ProductChatTransport` 隐藏。推荐语义：

```text

```

流程：

```text

→ request ownership
→ inspect Product RequestRun
→ if active: StreamResumeStore.resume(str(request_id))
→ if no active transport: return 204 / durable reconciliation response
```

P0 默认：

```text

```

重新 replay 当前 active assistant stream，不要求浏览器保存 Redis/cursor identity。

## 11.10 AI SDK Native Resume Caveat

AI SDK 当前官方文档明确提示：stream resumption 与 abort/`stop()` 存在兼容限制，页面 refresh/关闭也会触发 abort signal。因此 v8.2 **不把 `useChat({ resume: true })` 单独视为生产方案已经完成**。

M8 必须验证两种实现路径：

```text
A. native resume option + custom ProductChatTransport glue
B. Product-owned reconnect call / resumeStream orchestration
```

选择标准只有一个：

> Browser disconnect 必须只断 subscriber，不能向 Product execution 传播 cancel。

## 11.11 Product Stop != AI SDK stop()

产品 Stop：

```text
User Stop
→ useProductChat.cancelRequest()
→ POST /requests/{request_id}/cancel
→ Product CAS
→ PydanticAI first-party cancellation
→ Product terminal projection
```

不得把：

```text

```

直接当业务 cancellation SOT。底层 browser abort 是否作为 UI cleanup 辅助动作，只能在 Product terminal 已确定且经过 E2E Gate 后使用。

## 11.12 Multi-replica Resume

```text
Agent producer on FastAPI A
        │
        ├ in-memory backlog
        └ Redis Pub/Sub
                ▲
                │ resume request
Browser → LB → FastAPI B
                │
                └ subscriber stream
```

不要求 sticky session，只要 A 仍存活并且 A/B 共享 Redis。

## 11.13 Process Crash Boundary

如果 producer FastAPI A hard crash：

```text
execution task lost
producer-memory backlog lost
```

Redis 只能保留有限 transport state/coordination，不能凭空重建 Agent Python execution。

因此：

```text
Active Stream Resume ≠ Execution Durability
```

M8 需要 stale-active detection/reconciliation；未来 DBOS 才解决 crash/restart execution resume。

## 11.14 Partial Output Policy

```text
COMPLETED → assistant final durable PostgreSQL
FAILED/CANCELLED → partial output only active transport window
```

当前 Pub/Sub + producer-memory model 下，partial output 本来就不是长期 durable asset；这和 Product policy 一致。

# 13. Deadline / Retry / Cost Boundary

## 13.1 RequestRun Safety Deadline

Product Runtime 仍计算一次绝对 `deadline_at`：

```text
started_at + REQUEST_DEADLINE_SECONDS
```

但该值的产品语义是 **RequestRun emergency wall-clock safety cap**，用于终止 runaway / zombie execution，不是普通 Chat 或 Deep Research 必须完成的短 SLA。当前默认值为 900 秒。

正常执行由更靠近故障源的独立边界负责：

```text
external tool call  → tool-owned hard timeout（当前 30s 级）
model RPC           → LITELLM_CLIENT_TIMEOUT_SECONDS（当前 240s）
Main loop           → MAIN_* usage limits
Research child      → RESEARCH_AGENT_* usage limits
user stop           → Product explicit cancellation
whole RequestRun    → REQUEST_DEADLINE_SECONDS emergency cap（当前 900s）
```

PydanticAIExecutor 不把 Product `deadline_at` 重新切成每个 model step 的 remaining budget；每次模型 RPC 获得自己的固定 RPC timeout。这样一个合法的多步 Research 不会因为累计 wall-clock 超过 5 分钟而被误杀，同时单次 provider/tool hang、无限 Agent loop 和用户主动 Stop 仍分别受控。

Product safety cap 到期时，Product Runtime / ExecutionSupervisor 仍负责取消运行中的执行并提交 `REQUEST_DEADLINE_EXCEEDED` terminal；迟到 final 不具备 assistant write 资格。Streaming 继续保持 subscriber-independent task ownership，HTTP disconnect 不等于 Product Cancel。

## 13.2 Retry Ownership

```text
LiteLLM       → provider/deployment bounded retry/fallback
Agent         → semantic/tool retry（受 Product budget 限制）
Product       → 不透明失败后的业务 retry/idempotency
```

每层 retry 不能叠加成无限成本。

## 13.3 Cost Attribution

M7 后：

```text
request_id
→ one/many LiteLLM call ids
→ usage rows
→ user/conversation/agent_role
```

Product billing 以 business usage 为准，LiteLLM 数据作为 gateway evidence，不直接取代业务账本。

这里的“业务 usage”为归因账本，不表示 Product 自己重算供应商价格：权威 cost 和实际 deployment 仍以 LiteLLM evidence 为来源。PydanticAI success result 提供的 per-call token snapshot 是前置证据，不覆盖失败/cancel/timeout 或未来 Subagent 的所有已计费 attempt。


```text

keep shared Redis client ownership with app infra
```

不能把被部署中断的 execution 标成 Product COMPLETED。

# 18. Future DBOS Boundary

DBOS 不进入当前 clean baseline，也不进入 M8 第一版。

它未来只解决：

```text
execution durable workflow
crash/restart recovery
long-running steps
worker handoff
```

演进关系：

```text
M8 In-process ExecutionSupervisor
        ↓ implementation evolution
DBOS-backed Durable Execution Supervisor / Workflow
```

Product-facing contract 尽量不变：

```text
RequestRun
AgentExecutionRequest
AgentExecutor
Product terminal callback
```

DBOS 不能替代：

```text
PostgreSQL Product DB
StreamResumeStore active UI stream resume
RequestRun business lifecycle
```

引入 gate：

1. 已经有真实 restart-loss 问题。
2. Agent execution 与 HTTP subscriber 已解耦。
3. 请求时长/worker isolation 产生运维收益。
4. 用 failure drill 证明收益大于复杂度。

# 22. Hard Gates / Architecture Fitness Functions

## Gate 1 - Framework Replaceability

把 PydanticAI 换掉时，不应修改：

```text
Conversation schema
RequestRun schema
Auth/AuthZ
Billing semantics
Product API lifecycle
StreamResumeStore contract
```

## Gate 2 - Business SOT

只读取 Product DB 就能回答：

```text
用户发了什么？
请求状态是什么？
是否取消？
最终回答是什么？
成本归属给谁？
```

## Gate 3 - Authoritative History

```text
client messages ≠ authentic Product history
Product DB → AgentExecutionRequest.history
```

Agent implementation 不反向查询 Product repository。

## Gate 4 - Disconnect

```text
F5/network disconnect
→ execution continues
→ RequestRun remains RUNNING unless another terminal race wins
```

当前代码已清除 disconnect_checker cancel behavior；后续 Step 8 仍需真实 F5、cross-replica 与 204 reconciliation E2E。

## Gate 5 - No Duplicate Runtime

不得让：

```text
StreamState
Pydantic run state
Agent checkpoint state
```

成为第二套 Product RequestRun SOT。

## Gate 6 - Protocol Boundary

```text
PydanticAI internal event
→ official Vercel adapter
→ opaque encoded UI chunks
→ StreamResumeStore
→ Browser AI SDK protocol
```

StreamResumeStore 不解析/重写 AI protocol。

## Gate 7 - Terminal Authority

```text
assistant final + RequestRun completed COMMIT
→ THEN success finish UI event
```

Product COMMIT 后 transport emit failure不能回滚 Product state。

## Gate 8 - Execution Ownership

任何 active request 必须能回答：

```text
哪个 component owns task?
谁负责 deadline?
谁接受 cancel?
shutdown 怎么处理?
crash 后能否恢复?
```

M8：ExecutionSupervisor；crash durable = NO。

## Gate 9 - Stream Resume Ownership

任何 reconnect 必须能回答：

```text
stream identity? request_id
protocol owner? Vercel AI adapter / AI SDK
resume owner? StreamResumeStore
Redis role? state + Pub/Sub coordination
business SOT? PostgreSQL
```

## Gate 10 - Stop / Resume Semantics

```text
Product Stop != browser fetch abort
Product Stop != StreamResumeStore.close
Network disconnect != Product Cancel
```

AI SDK native resume/abort compatibility必须 E2E contract-test。

## Gate 11 - Process Crash Honesty

M8 不得宣称：

```text
producer process crash 可无损恢复
```

除非 DBOS/Temporal 等 durable execution 已正式落地并验证。

# 23. 明确禁止的架构

```text
❌ Conversation == Agent Thread
❌ Product DB 存 pydantic/langgraph framework identity 作为核心字段
❌ Agent Framework 负责业务幂等/计费/AuthZ
❌ HTTP disconnect == Product cancel
❌ StreamState == RequestRunStatus
❌ Redis Pub/Sub / Redis Stream == Business Message SOT
```

# 24. 技术决策摘要（ADR Index）

## ADR-A01 Product Runtime

**Accepted：FastAPI modular monolith。**  
Product lifecycle、数据库、Agent orchestration 均在 Python 生态，不增加无收益 Node/Hono Product service。

## ADR-A02 Agent Runtime

**Accepted：PydanticAI behind AgentExecutor。**  
PydanticAI 是 execution engine，不是 Product platform。

## ADR-A03 Agent History Boundary

**Accepted：Product Runtime 构造 server-authoritative `AgentExecutionRequest.history`。**  
Agent implementation 不反向读取 Product repository。

## ADR-A04 Harness

**Accepted with pinning：Pydantic AI Harness。**  
只按真实需要组合 capability，隔离 framework types。

## ADR-A05 Frontend AI Runtime

**Accepted：Vercel AI SDK UI。**  
`useChat` / ChatTransport / UIMessage protocol；M8 pin major + protocol tests。

## ADR-A06 AI Components

**Preferred with Package Gate：AI Elements。**  
作为 view primitives，不引入第二 Product/Thread runtime。

## ADR-A07 Model Gateway

**Accepted：LiteLLM Proxy。**  
production provider routing、credentials、fallback、gateway cost policy 集中管理。

## ADR-A08 Durability Split

```text
PostgreSQL            = Business Durability
StreamResumeStore     = Active UI Stream Resume
DBOS/Temporal future  = Execution Durability
```

三者不可混为 checkpoint。

## ADR-A09 Stream Resume Port

**Accepted：project-owned `StreamResumeStore` contract。**  
不 fork/绑定小型第三方 Alpha package；Product 依赖 contract，不依赖特定 replay backend。

## ADR-A10 Current Stream Backend

**Accepted for M8 implementation：`RedisStreamResumeStore`。**  
Redis KV/state + Pub/Sub + producer-memory replay；Redis client 注入；不使用 Redis Streams 作为默认 per-chunk durable log。

## ADR-A11 Stream Identity

**Accepted：`stream_id = str(request_id)`。**  
不建立第二 business stream identity。

## ADR-A12 Execution Supervision

**Accepted：M8 in-process ExecutionSupervisor。**  
HTTP subscriber 与 execution 解耦；明确 non crash-durable。

## ADR-A13 Terminal Event Gate

**Accepted：Product Runtime owns terminal event authority。**  
completed 只有 Product Success TX COMMIT 后可见。

## ADR-A14 Product Stop

**Accepted：Product cancel endpoint + Product CAS + first-party Agent cancellation。**  
不把 AI SDK `stop()` 直接当 Product Stop。

## ADR-A15 Redis Streams

**SUPERSEDED AS DEFAULT。**  
未来如果 benchmark 证明必要，只能作为 `StreamResumeStore` 的可替换 backend implementation，不改变 browser/Product contract。

# 26. 最终结论

v8.2 的最终架构不由某一个 Agent Framework 或某一种 Redis 数据结构定义，而由清晰的 ownership 定义：

```text
Product Runtime       = Business Control Plane
Agent Runtime         = Execution Engine
AI SDK UI             = Browser AI presentation/transport protocol
StreamResumeStore     = Active stream re-attachment port
PostgreSQL            = Business SOT
Redis                 = Distributed coordination
LiteLLM               = Production model gateway
DBOS future           = Execution durability
```

最终目标：

```text
React + Vite
  ↓
AI Elements + shadcn/ui
  ↓
Vercel AI SDK UI / ProductChatTransport
  ↓
FastAPI Product Runtime
  ↓
Product Start TX + authoritative history
  ↓
ExecutionSupervisor
  ↓
AgentExecutor
  ↓
PydanticAI + Harness
  ↓
LiteLLM

PydanticAI event stream
  ↓
VercelAIAdapter
  ↓
Product Terminal Gate
  ↓
StreamResumeStore
  ↓
RedisStreamResumeStore
  ↓
Browser subscriber / reconnect

PostgreSQL = durable Product truth
```

当前仓库已经完成一个关键前置动作：`StreamResumeStore` infra 已落地，因此 M8 不需要再发明 Redis Streams replay protocol。下一步工程重点是把 **Product lifecycle、ExecutionSupervisor、PydanticAI Vercel adapter、StreamResumeStore 和 ProductChatTransport** 正确接起来，并通过 F5/Stop/terminal-commit/multi-replica failure drill。

最后冻结四条原则：

> **分的是 ownership，不是机器。**  
> **Product Runtime 必须唯一。**  
> **Active Stream Resume 不等于 Execution Durability。**  
> **任何 UI success terminal event 都不得早于 Product COMMIT。**
