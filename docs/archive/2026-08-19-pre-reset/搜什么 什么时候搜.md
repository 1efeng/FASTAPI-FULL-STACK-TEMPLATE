这个问题就是下一阶段架构的核心：

> **不是“怎么让 Agent 搜”，而是“什么时候值得搜索，以及搜索什么才有价值”。**

结合前面的实验，我们已经可以确定：

- LLM 负责提出旅行方案 ✅
- Search 负责验证现实约束 ✅
- Search 不负责创造旅行方案 ❌

所以搜索决策应该围绕：

> **哪些未知信息如果错误，会导致整个方案失败或明显变差？**

---

# Research Decision Framework v1

## 1. 什么时候需要搜索？

不是看到旅行请求就搜索。

应该经过：

```
用户输入
    ↓
Intent Understanding
    ↓
Candidate Plan
    ↓
Decision Risk Analysis
    ↓
判断是否需要 Research
```

---

# 2. 搜索触发条件

定义 5 类。

---

# Rule 1：动态事实（必须搜）

特点：

> 会随着时间变化。

例如：

## 景点

需要：

- 是否开放
- 闭馆日期
- 当前票价
- 预约规则


例：

Candidate:

```
8月27日故宫
```

生成：

Research Question:

```
验证：
2026年8月27日故宫是否开放？
门票多少钱？
是否需要预约？
```

---

## 交通

需要：

- 班次
- 时间
- 价格

例如：

```
第三天16:00高铁返郑州
```

需要：

```
北京西→郑州东
下午有哪些车？
耗时？
价格？
```

---

# Rule 2：高风险决策（必须搜）

判断：

如果错误会导致：

- 行程失败
- 大量时间浪费
- 用户体验下降

必须查。

---

例如：

## 长城

Candidate：

```
Day2 八达岭
```

风险：

高。

因为：

- 距离远
- 往返时间长
- 影响整天安排


Research：

```
八达岭往返交通是否适合3日情侣行？
```

---

# Rule 3：用户明确要求（必须搜）

例如：

用户：

> 帮我找评分最高的情侣餐厅

必须搜索。


---

# Rule 4：价格敏感（建议搜）

预算紧：

例如：

5000预算：

需要：

- 高铁
- 酒店
- 门票


因为价格影响方案。

---

# Rule 5：体验优化（低优先级）

例如：

咖啡馆：

```
推荐几个拍照好的咖啡馆
```

可以搜索。

但是不能阻塞主流程。

---

# 3. 什么不需要搜索？

非常重要。

---

## 稳定知识

不要搜：

例如：

```
故宫是明清皇宫
长城历史悠久
```

LLM 已经知道。


---

## 泛化建议

不要搜：

```
北京情侣怎么玩
```

这就是 Search Agent 常犯错误。


---

## 已经确定不会改变决策的信息

例如：

模型决定：

```
晚上前门散步
```

不需要搜：

```
前门有什么历史
```

---

# 4. 搜什么？

不是关键词。

应该生成：

## Research Question

而不是：

```
北京旅游攻略
```

---

错误：

```
搜索：
北京八月旅游
```

结果：

大量无用信息。


---

正确：

```
Question:
8月27日八达岭长城开放吗？

Reason:
决定是否安排第二天长城

Impact:
High
```

---

# Research Question Schema

建议：

```json
{
  "question":
  "2026-08-27八达岭长城开放时间和预约要求",

  "category":
  "attraction_validation",

  "related_plan":
  "Day2 八达岭",

  "impact":
  "high",

  "why_needed":
  "如果无法进入，需要调整整日路线"
}
```

---

# 5. 如何搜索？

不同问题，不同工具。

不要所有问题都 web search。

---

## 第一优先：结构化 API

适合：

### POI

查询：

- 地址
- 营业时间
- 坐标


### Maps

查询：

- 距离
- 路线
- 时间


### Railway

查询：

- 班次
- 价格


---

## 第二优先：官方来源

适合：

### 景区

例如：

故宫：

优先：

官方预约系统。


---

## 第三优先：Web Search

用于：

- 无 API 信息
- 小众体验
- 评论

例如：

```
情侣晚上适合去哪散步
```

---

# 6. Search Budget 控制

每个 Candidate Plan：

不要无限搜。

设置：

## High Impact

最多：

3-5个问题。


## Medium

1-3个。


## Low

不阻塞。

---

例如北京案例：

Candidate:

```
D1 故宫
D2 长城
D3 天坛
```

Research：

只需要：

```
1. 故宫预约规则
2. 八达岭交通
3. 高铁返程
4. 天气风险
```

而不是：

```
搜索100篇北京攻略
```

---

# 7. 最终 Agent 流程

应该变成：

```
User
 |
 |
Intent Agent
 |
 |
Candidate Planner
 |
 |
Plan Critic
 |
 |
Research Router
 |
 +------ no research
 |
 +------ research needed
              |
              |
        Question Generator
              |
              |
        Tool Selector
              |
              |
        Evidence Collector
              |
              |
        Plan Refinement
              |
              |
          Final Plan
```

# 结合目前实验的结论

以前：

```
搜索 → 规划
```

导致：

- token 高
- 信息过载
- 搜很多无关内容


未来：

```
规划 → 找漏洞 → 搜漏洞
```

这才是 Agent 和普通 Chatbot 的区别。

下一步应该写：

```
docs/research/
└── research-router-design-v1.md
```

把：

- 触发条件
- Question Schema
- Tool Selection
- Search Budget

冻结下来。

这份会直接决定后面 research_agent 是否还需要存在，以及怎么改造。
