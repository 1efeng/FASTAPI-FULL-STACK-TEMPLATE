这个文档现在应该作为**产品边界定义文档**，因为它决定后面所有架构。

核心不是讨论“LLM 强不强”，而是：

> 在不给任何额外能力的情况下，LLM 已经能完成什么？  
> 一个优秀 Travel Agent 产品还需要什么？  
> 中间差距如何通过产品架构补齐？

下面整理成文档形式。

# LLM Baseline 与理想 Travel Agent 差距分析 v1

## 1. 实验背景

通过 Ideal User Input 实验：

固定用户输入：

> 我和女朋友计划8月26日从郑州去北京玩3天。第一次一起去北京，希望留下比较好的共同回忆。希望体验北京经典文化，有适合情侣拍照和散步的地方，吃北京特色美食，不希望每天赶很多景点。

分别测试：

1. DeepSeek V4 Flash 无联网
2. DeepSeek V4 Flash + Web Search

目标：

确认：

- 当前通用 LLM 能力边界
- Travel Agent 产品真正需要补充的能力

---

# 2. 当前 LLM 已经可以提供什么

## 2.1 用户需求理解（强）

LLM 可以理解：

### 基础约束

例如：

- 出发地
- 目的地
- 时间
- 人数
- 预算

---

### 隐含需求

例如：

用户说：

> 第一次和女朋友去北京，希望留下共同回忆

LLM 能推断：

- 不应该高强度赶景点
- 需要拍照场景
- 需要浪漫体验
- 需要安排散步时间

这是传统旅游搜索无法做到的。

---

## 2.2 Candidate Plan 生成（强）

LLM 可以生成：

- 每日路线
- 景点组合
- 节奏安排
- 餐饮建议
- 住宿区域

例如：

```
Day1:
故宫
景山
前门

Day2:
什刹海
胡同

Day3:
天坛
返程
```

已经具备旅行规划雏形。

---

## 2.3 体验设计能力（中强）

LLM 不只是罗列 POI。

它可以创造：

例如：

情侣：

```
下午：
故宫

傍晚：
景山看日落

晚上：
什刹海散步
```

形成：

文化 + 情绪 + 场景

这是普通搜索无法提供的。

---

## 2.4 自然语言交互能力（强）

LLM 可以：

- 解释原因
- 接受调整
- 根据反馈修改

例如：

用户：

> 不想走太多路

LLM：

调整：

- 减少景点
- 增加休息时间

---

# 3. 当前 LLM 不足什么

---

# 3.1 缺少目的地价值排序（最大问题）

实验发现：

无论联网还是不联网：

模型都没有稳定选择：

> 对这个用户来说，最值得去什么？

例如：

第一次北京：

应该考虑：

```
故宫
长城
天安门
```

但是模型可能选择：

```
恭王府
五道营
咖啡馆
```

原因：

LLM 知道很多地方。

但是不知道：

不同用户场景下：

哪个价值最高。


---

## 需要补：

Destination Intelligence Layer

例如：

北京：

```
first_visit:
  must_have:
    - 故宫
    - 长城
    - 天安门

couple:
  experience:
    - 景山日落
    - 什刹海夜景

family:
    - 颐和园
```

作用：

告诉模型：

不是有什么。

而是什么值得优先。

---

# 3.2 缺少真实世界验证能力

LLM 会生成：

```
8月26下午去故宫
```

但是不知道：

- 是否开放
- 是否预约
- 门票多少
- 是否施工
- 排队多久


---

## 需要补：

Reality Layer

负责：

验证：

```
景点状态
票务
交通
天气
营业时间
```

来源：

- 官方 API
- POI API
- Maps
- Search


---

# 3.3 缺少决策取舍能力

旅行不是信息堆积。

核心问题：

> 如果只能选3个体验，选什么？


LLM 容易：

```
故宫
天坛
颐和园
长城
什刹海
```

全部想安排。


但是优秀产品应该：

主动：

```
保留：
故宫
长城

舍弃：
某个园林

原因：
第一次北京价值更高
```

---

## 需要补：

Decision Critic

负责：

评价 Candidate Plan：

```
是否符合用户目标？

是否过载？

是否遗漏核心体验？

是否值得牺牲？
```

---

# 3.4 缺少持续个性化

当前 LLM：

一次输入一次输出。

不知道：

- 用户历史旅行
- 喜欢什么节奏
- 去过哪些地方


---

## 需要补：

User Preference Memory

例如：

```
用户A:

喜欢：
文化
慢节奏

不喜欢：
排队
购物

过去：
去过上海博物馆
```

---

# 3.5 缺少可靠预算能力

LLM 可以估算。

但是：

容易：

- 加法错误
- 漏项
- 价格过期


---

## 需要补：

Budget Engine

负责：

```
交通
住宿
门票
餐饮
备用金
```

精确计算。

---

# 4. Web Search 的正确定位

实验结论：

Web Search：

提升：

✅ 动态事实

例如：

- 门票
- 预约
- 开放时间


不能解决：

❌ 用户价值判断

不能替代：

- 产品知识
- 决策能力

---

所以：

错误：

```
Search
 ↓
Plan
```

正确：

```
Plan
 ↓
Need Verification
 ↓
Search
```

# 5. 理想 Travel Agent 架构

最终能力：

```
                 User

                  ↓

        Intent Understanding
        （理解旅行目的）

                  ↓

        Destination Intelligence
        （目的地价值排序）

                  ↓

        Candidate Planner
        （生成候选方案）

                  ↓

        Decision Critic
        （发现问题和取舍）

                  ↓

        Research Router
        （只验证关键事实）

                  ↓

        Reality Layer
        （真实世界数据）

                  ↓

        Final Planner

                  ↓

             Travel Plan
```

# 6. 差距补齐路线

## Phase 1：补领域认知

目标：

超过普通 LLM。

实现：

- Destination Knowledge
- POI Ranking
- Experience Templates


---

## Phase 2：补事实可靠

实现：

- POI API
- Maps
- Ticket
- Weather
- Transport


---

## Phase 3：补决策能力

实现：

- Candidate Plan
- Plan Critic
- Research Router


---

## Phase 4：补长期价值

实现：

- User Memory
- Feedback Loop
- Personalized Ranking


---

# 最终结论

当前 LLM 已经可以完成：

> 一个不错的旅行顾问。

但是距离优秀 Travel Agent 还缺：

1. **知道什么最值得选择**
2. **知道哪些事实必须确认**
3. **知道什么时候应该取舍**
4. **记住用户长期偏好**

所以产品核心不是：

> 让模型搜索更多。

而是：

> 给模型增加旅行领域决策能力，让它从“会写攻略”升级为“会做旅行决策”。

---

这份应该成为后续架构文档的总纲，优先级甚至高于 Agent 设计。
