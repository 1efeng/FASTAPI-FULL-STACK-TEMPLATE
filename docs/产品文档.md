# 行伴 Travel Agent v8 产品文档

> 文档状态：2026-08-13 v8 clean baseline  
> 当前阶段：CLI Agent 核心能力验证完成，生产 P0 建设阶段  
> 产品方向：面向 C 端用户的通用旅行 Agent  
> 统一设计基线：**最低 10,000 DAU 的 C 端生产产品**

---

# 1. 产品愿景

行伴希望让普通用户通过自然语言完成一次旅行从“有想法”到“可执行方案”的主要决策过程。

用户可以直接说：

```text
“8 月 20 日东京进，24 日大阪出，两个人，舒服一点，帮我安排。”
```

计划生成后可以继续说：

```text
“第二天不要那么赶。”
“预算压低一点。”
“环球影城换到第三天。”
```

产品不要求用户理解：

```text
Agent
SubAgent
Skill
Tool Call
LiteLLM
Provider
Trace
```

用户只关心：

```text
我说的话系统有没有理解？
信息是不是现在还有效？
路线是否真实可执行？
预算是否靠谱？
能不能继续改？
失败时会不会乱编？
明天回来还能不能继续？
```

# 2. 产品核心价值

## 2.1 自然语言规划

用户不需要填写复杂旅行表单；只有真正改变路线、日期、预算边界或旅行者限制的信息才进行必要澄清。

## 2.2 当前事实

对会变化的信息，产品通过 Research / Tool 获取当前事实，而不是把模型训练记忆伪装成实时数据。

包括：

- 票价；
- 开放时间；
- 预约规则；
- 临时闭馆；
- 铁路 / 航空规则；
- Pass；
- 签证 / 入境规则；
- 天气；
- 汇率。

## 2.3 方案取舍

产品不是“景点清单生成器”，而是结合：

```text
日期
进出城市
天数
预算
旅行者
兴趣
节奏
交通
当前事实
```

形成真正可执行的路线。

## 2.4 可持续修改

用户不需要每次从零描述全部背景。

产品以最近一版完整计划为基础，理解修改范围，只重新 Research 受影响事实，再生成新的完整版本。

## 2.5 预算可靠

预算总和由确定性工具计算，不让模型自由心算多个费用项。

## 2.6 故障时可信

外部服务失败后：

```text
可以降级 → 明确降级继续
不能继续 → 明确失败
```

绝不使用“看起来合理”的旧知识冒充当前事实。

# 3. 产品用户

主要面向：

- 第一次去某个目的地的自由行用户；
- 有大致日期和目的地，但不想做数小时攻略的用户；
- 已经有零散信息但不会组合路线的用户；
- 已经有行程，希望快速修改的用户；
- 需要查询当前旅行事实的用户。

核心 Jobs To Be Done：

```text
去哪？
什么时候去？
怎么走？

会不会太赶？
住哪里？
多少钱？
现在这个信息还有效吗？
改变想法以后怎么改？
```

# 5. 产品交互原则

## 5.1 普通问答不强制规划

用户问：

```text
“东京明天天气怎么样？”
“京都到大阪多久？”
“推荐几个京都寺庙。”
```

就回答该问题，不强制激活完整规划。

## 5.2 只澄清真正改变方案的问题

不机械追问十几个偏好字段。

只有缺失信息会显著改变：

- 日期；
- 进出城市；
- 核心路线；
- 特殊旅行者约束；
- 关键预算边界；
- 其他方案级选择

时才进行澄清。

## 5.3 Pass 不预设结论

JR Pass、城市 Pass、交通套票必须根据最终路线和当前价格比较，不先决定“游客就应该买”。

## 5.4 不暴露内部技术术语

用户不看到：

```text
LiteLLM cooldown
Request deadline
SubAgent
Provider SDK
OTel span
```

只看到：

```text
正在处理
正在查询当前信息
正在生成行程
服务暂时繁忙
部分信息暂时无法核实
额度已用完
请求没有权限
```

# 6. 核心用户旅程

## 6.1 创建完整计划

```text
用户输入需求
 ↓
必要澄清
 ↓
当前事实 Research
 ↓
比较路线 / 交通 / Pass
 ↓
形成完整计划
 ↓
预算汇总
 ↓
用户继续修改
```

用户预期：

- 不重复问已经知道的信息；
- 规划期间不是长时间空白；
- 路线前后一致；
- 预算与最终方案一致；
- 当前事实有来源和新鲜度；
- 失败时不虚构。

## 6.2 修改计划

```text
打开历史会话
 ↓
“第二天轻松一点”
 ↓
理解受影响范围
 ↓
只补充必要 Research
 ↓
重新计算受影响预算
 ↓
返回完整修订版
```

## 6.3 单点事实查询

快速回答，不进入完整规划。

## 6.4 Tool 局部失败

```text
Weather fail
→ 行程继续
→ 明确天气未核实

FX fail
→ 保留当地货币

Maps fail
→ 继续做区域级安排
→ 不承诺精确耗时
```

## 6.5 模型故障

```text
Primary Model fail
 ↓
LiteLLM retry / fallback
 ↓
Fallback Model
 ↓
成功 → 用户无感继续
全部失败 → 产品级统一错误
```

用户不需要知道 Provider 名称。

# 7. 完整旅行计划输出 Contract

完整计划核心结构：

```text
## 行程概览
## 行前准备
## Day N｜主题 / 区域
## 住宿建议
## 美食建议
## 预算参考
## 出行提醒
```

第一阶段仍以 Markdown 作为语义 Source of Truth。

当前不做重型 Plan CRUD / Renderer / Writer Agent。

前端可以按 Markdown 或结构化 SSE 事件展示，但不改变 Agent 的核心语义 Contract。

# 8. C 端 Streaming 体验

生产使用 FastAPI Agent Streaming Adapter；底层 transport 和官方 wire protocol 在 M8 Streaming Spike 后按锁定版本确定，产品不把某种 SSE 事件名当作协议 SOT。

产品只定义用户可见阶段语义，例如理解需求、查询信息、整理方案、生成最终回答；这些状态由 Adapter 按官方协议投影，不等于 Agent 私有推理过程。

典型 status：

```text
正在理解你的旅行需求…
正在查询最新旅行信息…
正在比较路线…
正在整理预算…
正在生成最终行程…
```

不展示 Chain of Thought。

基础 transport keep-alive 由框架实现，不需要作为用户可见产品状态。

---

# 9. 请求可靠性体验

## 9.1 Idempotency

用户网络抖动导致客户端重试时，同一个请求不能重复烧完整 Agent 成本。

```text
same user + same Idempotency-Key
→ 返回已有 request / result
```

## 9.2 请求状态

用户离开页面或连接断开后，可以查询：

```text
running
completed
failed
cancelled
```

## 9.3 Final 可恢复

产品必须做到：

```text
最终结果先持久化
 ↓
再发送 SSE final
```

即使 SSE final 丢失，重新打开会话仍能看到结果。

## 9.4 End-to-End Deadline

用户请求不能因为多个模型 retry / Tool timeout 无限等待。

整体请求有产品级 Deadline；LiteLLM 只处理单次模型调用内部的 retry / fallback。

# 10. 会话与长期使用体验

正式 C 端应支持：

```text
今天生成计划
 ↓
关闭 App
 ↓
明天回来
 ↓
继续修改同一个计划
```

用户不需要理解 checkpoint。

技术上由：

- Business conversation/message persistence（PostgreSQL）；
- RequestRun 运行状态与事件流（Redis Stream）

共同完成。

产品不承诺“把所有历史原文永久塞给模型”；长会话会进行安全的上下文管理。

# 13. AI 成本产品策略

AI 成本必须是产品能力，不是月底再看账单。

最新职责：

```text
LiteLLM
→ token / actual model / response cost / spend

Travel Agent
→ 业务归因：哪个用户 / request / Main / Researcher / 功能
```

产品至少需要看到：

- 每完整规划平均成本；
- Main / Researcher 成本占比；
- 每用户日均 AI 成本；
- model group / actual model 分布；
- fallback 额外成本；
- Idempotency 避免的重复成本。

不再自己维护一套模型定价引擎作为 P0。

# 17. P0：达到最低 10,000 DAU C 端基线

## P0-1 LiteLLM Gateway Integration & Reliability

产品保证：单个模型 Provider 的限流、超时、短时故障不会直接变成用户 500；同时不会因多层 retry 让用户等待数分钟。

## P0-2 Tool Resilience / Partial Degradation

Search / Maps / Weather / FX 独立故障策略。

## P0-3 Trace + 最小基础设施 instrumentation

从用户 Request 到 Agent / Gateway / Tool / DB 可以定位（OpenTelemetry 按需；AI trace 平台 M10 再决策）。

## P0-4 LLM Business Usage Attribution

LiteLLM 提供成本事实，Travel Agent 完成产品归因。

## P0-5 Agent Streaming Adapter + Request Lifecycle

包含：

```text
Idempotency
request status
End-to-End Deadline
cancel
final durable before final event
unified error
health / readiness
```

## P0-6 Conversation Persistence + Context

跨实例 / 跨设备可恢复；durability 由 PostgreSQL / Redis Stream 承担，不自研 checkpoint schema / summary engine。

## P0-7 Auth + Authorization + Abuse Protection

真实用户体系、资源所有权、quota / rate / concurrency。

## P0-8 Critical Research Trust

关键旅行事实必须有来源、新鲜度和不确定性处理。

## P0-9 Security & Data Governance

PII / Secret / Trace / Retention / Delete / Third-party boundary。

## P0-10 Basic Executable Eval Gate

pytest + Basic Eval（AI trace 平台 M10 再决策）。

## P0-11 Production Data + Multi-instance Deployment

Business DB、Redis Stream 事件流、LiteLLM DB、Redis、Backup/Restore、App/Gateway 多实例、压测、rollback。

## P0-12 C-End Client + Gray Release

至少一个正式 Web / Mini Program / App Client。

# 23. 产品决策原则

1. **最低按 10,000 DAU 设计，但不过度架构。**
2. **框架能稳定解决的基础能力优先复用。**
3. **实时事实来自可核验数据源。**
4. **模型做语义决策，代码做确定性边界。**
5. **失败不可伪造。**
6. **Final 必须可恢复。**
7. **成本优化必须经过 Trace + Eval。**
8. **产品成功取决于用户结果，不取决于 Agent 数量。**
