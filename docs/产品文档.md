# 行伴 Travel Agent 产品文档

> 状态：RESET DRAFT 0.1
> 日期：2026-08-19
> 角色：当前唯一 Product SOT
> 原则：从用户价值出发，不继承 reset 前的产品流程、Agent 设计、Research 设计或工具设计。

---

# 1. 产品要解决的问题

用户真正需要的不是一份“景点列表”，也不是一堆“旅游信息”。

用户需要的是：

> **在自己的时间、预算、同行者和现实条件下，得到一趟值得去、能够执行、符合这次旅行目的的旅行方案。**

因此产品的目标不是信息完整度最大化，而是旅行结果最大化。

---

# 2. 用户最终想从旅行中得到什么

一次旅行可能同时服务多个目标，例如：

```text
亲密陪伴 / 创造共同记忆
陪父母 / 表达关心
经典地标打卡
品尝当地美食
文化理解
自然体验
放松恢复
摄影与分享
庆祝纪念日
探索新鲜事物
完成挑战 / 获得成就感
```

这些目标不是固定问卷选项，而是产品需要从用户表达中理解的旅行意图。

## 2.1 Trip Intent

`Trip Intent` 回答：

> **为什么进行这次旅行？旅行结束后，用户希望真正获得什么？**

它不同于普通偏好：

```text
Trip Intent
→ 最终想获得的旅行结果

Preference
→ 喜欢怎样旅行

POI / Activity
→ 实现这些结果的手段
```

同一个目的地、日期和预算，在不同 Trip Intent 下应该产生不同的方案。

---

# 3. 旅行的现实边界

产品必须尊重用户不能被规划随意改变的条件。

暂称为 `Trip Contract`，包括但不限于：

```text
出发地 / 返回地
目的地或候选目的地
日期 / 天数
人数与同行关系
总预算及预算口径
已经预订的交通 / 酒店 / 活动
必须参加的活动
不可改变的时间窗口
老人 / 儿童 / 行动能力等限制
饮食、证件或其他硬约束
```

这些条件来自用户和用户已确认的信息，不通过外部搜索“猜出来”。

---

# 4. 产品如何形成一次旅行

当前产品核心流程先定义为：

```text
理解 Trip Intent
        ↓
理解 Trip Contract / People / Preferences
        ↓
设计 Experience Strategy
        ↓
形成 Candidate Plan
        ↓
判断做主要旅行决策还缺什么上下文
        ↓
只获取最小充分 Planning Context
        ↓
判断方案是否可执行
        ↓
判断方案是否真正服务 Trip Intent
        ↓
必要时只修改受影响部分
        ↓
信息足够后停止调查
        ↓
输出 Final Plan
```

这里描述的是产品语义，不规定任何 Agent、Workflow、Tool 或框架实现。

---

# 5. Experience Strategy

产品不应该从“目的地 Top N POI”开始规划。

在选择具体景点、餐厅、酒店之前，应该先回答：

```text
这趟旅行最重要的体验是什么？
哪些体验必须有？
哪些只是可选？
节奏应该轻松还是高密度？
需要多少留白？
怎样的体验组合最符合 Trip Intent？
```

POI 是实现 Experience Strategy 的候选手段，不是产品目标本身。

---

# 6. Candidate Plan

Candidate Plan 是在有限信息下形成的第一版可解释方案。

它不要求一开始就掌握所有当前事实，只需要足够暴露主要旅行决策，例如：

```text
每天的核心体验
大致区域与顺序
住宿基地
主要跨城移动
关键时间锚点
预算结构
```

Candidate Plan 的价值是让产品知道：

> **哪些现实信息真的会改变这份计划。**

不知道某个事实，不等于必须查询这个事实。

---

# 7. Minimum Sufficient Planning Context

产品只应该获取足以做正确主要决策的最小上下文。

暂称：

> **Minimum Sufficient Planning Context（MSPC）**

判断一个信息是否值得获取，只问：

```text
1. 它的不同可能值会不会改变计划是否可执行？
2. 它的不同可能值会不会明显改变用户想获得的旅行结果？
```

如果两个答案都是否：

```text
→ 当前规划阶段不获取
```

例如：

```text
某个 5000 元总预算旅行中，小景点门票是 2 元还是 10 元
→ 通常不会改变路线和核心体验
→ 不值得为了精确而追加调查
```

而：

```text
核心景点目标日期是否开放
→ 会直接让某一天方案成立或失效
→ 属于必要 Planning Context
```

---

# 8. Planning Context 的基本问题

旅行计划要成立，至少需要在必要时回答以下几类问题：

## 8.1 Space

```text
地点在哪里？
地点之间如何移动？
路线是否存在不必要折返？
住宿基地是否合理？
```

## 8.2 Time

```text
活动与移动是否装得进时间窗口？
是否存在关键时间冲突？
是否需要合理缓冲？
```

## 8.3 Access

```text
用户在目标时间能否真正进入 / 使用这个体验？
是否存在开放、预约、容量、证件或运营限制？
```

## 8.4 Resources

```text
总预算是否成立？
时间和体力是否合理？
移动、行李和同行者负担是否可接受？
```

## 8.5 Outcome relevance

```text
哪些现实条件会明显影响 Trip Intent 的实现质量？
```

不同旅行目的下，同一个信息的重要性可以不同。

---

# 9. Planning 与 Execution 分离

产品必须区分：

```text
Planning Context
→ 用于判断总体方案是否成立、哪个方案更好

Execution Context
→ 临近出发时用于具体怎么买、几点走、能不能进
```

长期规划不默认追求：

```text
实时余票
实时房价
目标日期精确天气
当天临时运营状态
```

只有当前决策阶段确实需要时，才获取执行级信息。

---

# 10. 产品停止调查的能力

产品必须有明确 Stop Rule。

当：

```text
Trip Contract 已足够明确
主要路线在空间 / 时间 / Access / Resource 上已经可判断
已经能根据 Trip Intent 在主要候选方案间做选择
剩余未知不会明显改变主要方案或核心旅行结果
```

则：

> **停止继续获取信息，完成计划。**

继续为了“资料完整”调查，是产品缺陷而不是质量提升。

---

# 11. 什么叫一份好的旅行计划

当前至少从以下维度判断：

```text
Feasibility
→ 真实有机会执行

Intent Alignment
→ 服务用户真正想从旅行中获得的结果

Constraint Satisfaction
→ 时间、预算、同行者和已有安排不被违反

Experience Quality
→ 有节奏、有记忆点，不机械堆 POI

Evidence Sufficiency
→ 真正关键的动态条件具有足够现实依据

Information Economy
→ 没有为了完整而获取大量不改变决策的信息
```

## 11.1 关键事实与来源呈现

来源服务于用户判断行程能否执行，而不是展示搜索过程。

只有事实错误后会让核心行程失效时，最终计划才需要在对应内容旁就近提供直接来源，例如：

```text
必须预约或购票
闭馆、准入或运营限制
关键交通是否存在、末班衔接是否成立
足以取消活动的天气、政策或季节条件
```

普通推荐、评分、餐厅人均、价格小幅浮动和分钟级时刻可以采用合理区间并提醒确认，不要求逐项引用。产品不输出独立研究报告、搜索过程复述或为了数量而堆积的完整来源清单。

---

# 12. 产品非目标

当前明确不是：

```text
旅游百科全书
目的地 Top N 景点生成器
来源数量竞赛
所有事实实时精确化
所有未知信息补全系统
复杂旅游偏好问卷
为了展示联网能力而搜索
为了技术上的多 Agent 而改变用户体验
```

---

# 13. 当前待继续定义的产品问题

从 0 开始后，下一步只讨论产品问题，不提前讨论技术实现：

```text
1. Trip Intent 最小需要表达到什么程度？
2. 用户未明确表达 Trip Intent 时，产品何时推断、何时澄清？
3. Experience Strategy 的最低语义结构是什么？
4. Candidate Plan 什么程度算“足够形成”？
5. MSPC 的产品级判定规则是否还缺关键维度？
6. Planning Context 与 Execution Context 的边界如何对不同旅行时间跨度变化？
7. 修改已有计划时，哪些产品状态需要继承？
8. 最终计划怎样体现“为什么这样安排”而不是只给日程？
9. 产品 Eval 如何衡量 Intent Alignment 与 Information Economy？
```

这些问题确认后，再冻结 Product Baseline，并从它向下推导系统架构。
