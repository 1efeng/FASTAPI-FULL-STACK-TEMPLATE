# 生产部署契约

> 目标：最低 10,000 DAU baseline，可从单机多容器平滑迁移到多机，而不改业务架构。

# 1. 推荐拓扑

```text
Internet
  ↓
TLS / LB / Nginx
  ↓
FastAPI replicas
  ↓
Travel Agent
  ├── LiteLLM service
  ├── Tools
  ├── PostgreSQL
  └── Redis

LiteLLM service
  ↓
LiteLLM replicas
  ↓
Providers
```

# 2. 第一阶段

可以：

- 一组云主机 / container runtime；
- FastAPI 2+ replicas；
- LiteLLM 2+ replicas；
- Managed PostgreSQL；
- Managed Redis。

是否必须两台物理机器由 SLA 决定；架构必须不依赖单机本地状态。

# 3. Container

应用和 LiteLLM 可以 Docker 化。

Production 不使用漂移依赖：

- app image pin；
- LiteLLM image pin；
- `uv.lock`；
- config versioned。

# 4. PostgreSQL

逻辑数据域：

- business；
- LangGraph；
- LiteLLM。

可以同 server，migration ownership 分开。

# 5. Redis

Travel Agent 与 LiteLLM 可以共享 Redis 服务，但 prefix / ACL / logical separation 要明确。

# 6. Migration

Release 顺序必须设计：

```text
compatible DB migration
→ app / gateway rollout
→ validation
```

LiteLLM schema migration 按其官方版本流程，不由业务 migration 工具乱改内部表。

# 7. Health

FastAPI：

```text
/health/live
/health/ready
```

LiteLLM 使用其可用的 health/readiness 路径与外部 LB check。

# 8. Graceful Shutdown

需要：

- 停止接收新请求；
- 给 active SSE / Agent 合理结束或取消时间；
- request 状态不留下假 completed；
- DB connection clean close。

# 9. Backup / Restore

必须覆盖：

- business DB；
- LangGraph persistence；
- LiteLLM critical persisted config/spend（按需要）。

至少完成一次真实 restore drill。

# 10. Secrets

生产 Secret 通过部署平台注入。

不得 bake 到 image / repo。

# 11. Observability

上线必须同时有：

- structured logs；
- OTel；
- LangSmith（按策略）；
- platform metrics；
- alerts。

# 12. Rollback

Release 必须兼容：

- app rollback；
- LiteLLM config rollback；
- image rollback；
- DB forward-compatible migration strategy。

# 13. Capacity

最终规格通过：

- RPS；
- SSE；
- model concurrency；
- tokens；
- provider quotas；
- DB/Redis pool；
- Tool latency

压测决定。

# 14. 不要求

P0 不强制：

```text
Kubernetes
Kafka
Service Mesh
Redis Cluster
Postgres sharding
```

出现真实瓶颈再引入。
