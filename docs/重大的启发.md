# 从追求可靠回归到什么是一份好的旅游规划

对，沣。先把所有现有的 Reality Gap / VerificationItem / research_agent / Web Search 都放一边，从第一性原理重新定义。
我认为旅行规划的本质可以压成一句话：
旅行规划 = 在有限的时间、预算和人的约束下，在现实世界的空间网络中选择一组可执行的体验，并安排成一条整体效用最高的路径。

所以 Agent 真正需要的不是“旅游信息”，而是足以做这些决策的最小上下文。
一、先问：一个旅行计划为什么会失败？
假设已经生成：
D1 天坛 → 前门
D2 故宫 → 景山
D3 八达岭 → 回郑州
它失败，无非几类原因：
去不了
来不及
进不去
住不起
整体超预算
体力/偏好不合适
已经预订的东西冲突
现实发生变化
反过来推：
只要我们拥有足够判断这些问题的上下文，就拥有了规划旅行所需的上下文。

这比“把不知道的信息查出来”小很多。
二、旅行最底层其实只有 6 类 Context
我倾向于最终不要按“景点 / 酒店 / 火车 / 天气”分。
这些是业务对象，不是第一性原理。
真正稳定的抽象是：
Context	回答什么问题
Trip Contract	用户到底要什么
Space Context	地点之间是什么空间关系
Time Context	时间是否装得下
Access Context	人到底能不能获得这个服务/进入这个地方
Resource Context	钱、体力等资源是否够
Preference / Utility Context	哪个可行方案更值得选


再额外有一个贯穿所有 Context 的元属性：
Freshness / Uncertainty —— 这个信息现在需要多新、多准？

这个非常重要。
1. Trip Contract：先定义“这趟旅行是什么”
这是唯一几乎每次都必须拥有的 Context。
比如：
origin = 郑州
destination = 北京
start = 2026-08-26
end = 2026-08-28

party:
  adults = 2
  relation = couple

budget:
  total = 5000
  includes = round_trip_transport

preferences:
  classic_attractions
  moderate_pace

hard_constraints:
  return_by = Aug 28
再加已有 commitment：
已经买的机票
已经订的酒店
必须参加的活动
不能走很多路
带老人
带儿童
签证限制
这些东西：
不能搜索。
它们来自：
User
Conversation
Existing bookings / Product context
这是整个计划的边界条件。
2. Space Context：旅行首先是个空间问题
旅游说到底是在移动：
Origin
  ↓
City
  ↓
Hotel
  ↓
POI A
  ↓
POI B
  ↓
Station
  ↓
Home
因此 Planner 需要的不是“故宫百科”。
而是：
故宫在哪里
景山在哪里
天坛在哪里
酒店基地在哪里

故宫 → 景山多远
酒店 → 故宫多久
酒店 → 清河站多久
八达岭 → 北京西回程风险有多大
本质上是一张：
Travel Graph
Nodes
=
城市 / 车站 / 机场 / 酒店区域 / POI

Edges
=
距离 / 行程时间 / 交通方式 / 换乘成本
例如：
前门酒店
   │
   ├── 15 min → 天安门
   ├── 25 min → 故宫入口
   ├── 30 min → 北京西
   └── 50 min → 清河站
这时候你就会发现：
大量旅游规划根本不需要 Web Search。

应该来自：
POI API
Maps API
Route API
3. Time Context：不是知道“几点开门”，而是判断“装不装得下”
时间 Context 本质上由几个东西组成：
Trip time envelope

+

Activity duration

+

Travel duration

+

Availability window

+

Required buffers
例如 D3：
08:30 故宫
     ↓ 3h
11:30 出神武门
     ↓
午餐
     ↓
酒店取行李
     ↓
北京西
     ↓
16:00 高铁
Planner 真正需要知道的是：
这条链条是否在时间上成立。

因此：
故宫闭馆时间
本身不是目标。
它只是用于判断：
D3 故宫 + 下午返程
是否 feasible。
这会直接改变我们的搜索行为。
以前：
不知道闭馆几点
→ 搜
以后：
当前 Plan 是否需要这个时间窗口才能判断 feasibility？

YES → 获取
NO  → 不获取
4. Access Context：现实世界允许你做吗？
这是 Travel Agent 特别关键的一层。
因为：
地点存在
≠
用户能进去
例如：
故宫
Access Context 包括：
当天是否开放
是否需要预约
是否有容量限制
是否需要身份证/护照
是否存在年龄限制
是否需要门票
预约截止点
交通是否运营
是否需要签证/许可
但注意：
并不是这些字段每次都全部查询。
对于北京 case：
故宫是否开放
故宫是否必须预约
会影响计划成立。
所以需要。
而：
珍宝馆具体多少钱
如果我们根本没安排珍宝馆：
NO CONTEXT NEEDED
这就是 Planning Context 和事实搜集最大的区别。

最明显的是：

6. Preference / Utility Context：可行不等于好
前五项主要回答：
能不能做。

但旅行规划还得回答：
值不值得这样做。

比如：
方案 A：
故宫 + 天坛 + 颐和园 + 长城
每天暴走

方案 B：
故宫 + 长城 + 天坛
节奏舒服
二者都 feasible。
最终选择依赖：
couple
classic attractions
photography
relaxed
foodie
nightlife
family
nature
shopping
这就是 Utility Context。
它通常主要来自用户，不应该联网查。
三、然后还有一个极重要的 Meta Context：Freshness
这个不是第七种旅游信息。
而是每一个 Context Item 都要带的属性。
例如：
故宫坐标
freshness：
很低
几年不变。
所以 POI 数据即可。
故宫星期一闭馆
freshness：
中等
规则可能变化，但不是分钟级。
8月28日是否临时闭馆
freshness：
高
临近执行才有价值。
8月28日天气
7 天前：
精确 forecast 价值低
1 天前：
Execution Context
价值高
于是我们就得到一个非常重要的架构：
Planning Context ≠ Execution Context
四、Planning 阶段和 Execution 阶段必须分开
这是之前架构还没有完全抽象出来的地方。
Planning Context
回答：
这个方案总体能不能成立、哪个好？

需要：
大致交通时间
成本区间
景点可访问性
空间关系
住宿区域
预约要求
允许：
range
estimate
stable data
例如：
郑州→北京：
约 2–3.5h
约 ¥300–370 / 人单程
足够规划。
Execution Context
回答：
我现在具体怎么买、怎么进去、几点出发？

这才需要：
G336 07:xx
还有没有票
准确票价
具体酒店房价
8月27日实际天气
临时闭馆公告
今天长城限流情况
所以如果用户只是：
“帮我设计 10 月日本行程。”

Agent 不应该马上疯狂查：
实时酒店
实时车次
实时天气
它们此刻几乎没有决策价值。
五、这样我们能得到一个更重要的概念：Minimum Sufficient Planning Context
我建议正式定义一个：
MSPC — Minimum Sufficient Planning Context
意思是：
足以判断 Candidate Plan 可行性并在候选方案之间作出选择的最小外部上下文集合。

它不是“尽可能完整”。
而是：
再少一个重要 Context
→ 可能选错方案

再多一个 Context
→ 不会改变方案
就在这里停止。
六、判断某个信息要不要获取，只需要一个问题
以后 Main 不应该问：
“这个我知不知道？”

而应该问：
“这个信息的不同可能值，会不会改变当前旅行决策？”

例如：
景山票价
可能 ¥2
可能 ¥10
无论哪个：
D2 故宫 → 景山
都不变。
所以：
Context value = low
→ 不查
故宫当天是否开放
OPEN
→ D3 故宫

CLOSED
→ 整条 D3 重做
所以：
Context value = high
→ 必须获取
这其实就是决策理论里的 Value of Information 思路。
旅行 Agent 不应该追求：
information completeness

而应该追求：
decision sufficiency

因为：

八、这也会改变整个 Agent Architecture
我现在会把 Travel Planning 的核心流重新抽象成：
User Context
      ↓
Trip Contract
      ↓
Candidate Plan
      ↓
Planning Decisions
      ↓
Required Planning Context
      ↓
Context Acquisition
      │
      ├─ Already known
      ├─ Estimate
      ├─ POI
      ├─ Maps
      ├─ Weather
      ├─ Web
      └─ Research Agent
      ↓
Planning Context Snapshot
      ↓
Evaluate / Revise Plan
      ↓
Context sufficient?
      │
      ├─ NO → only acquire missing decision context
      │
      └─ YES
      ↓

      ↓
Final Plan
这里一个很大的变化是：
Reality Gaps
不再是核心对象。
核心对象变成：
Planning Decisions
        ↓
Context Requirements
这比“缺什么查什么”更稳。

十、Research Agent 在这个新模型里的位置也终于特别清楚
Context Acquisition Router：
一个 Context Requirement
        ↓

POI 能回答？
→ POI

Maps 能回答？
→ Maps

Weather 能回答？
→ Weather

简单动态事实？
→ Web Search

需要原文证据？
→ controlled fetch

一个 Context Requirement 实际包含
多个相互关联、evidence-heavy 的问题？
→ research_agent
所以 Research Agent 不再和 Main 抢“谁来查事实”。
它只是：
Context Acquisition 的一种昂贵但隔离良好的策略。

我认为这个定位比现在又清楚了一层。
最终可以把 Travel Agent 压缩成一句架构定义
Travel Agent 的工作不是收集旅行信息，而是在用户约束下构造 Candidate Plan，并按决策价值获取最小充分 Planning Context，直到能够可靠判断空间、时间、访问和资源可行性，然后停止获取信息并完成方案。

对应一句更短的工程原则：
Don't fill knowledge gaps.

Fill decision context.
我认为这应该成为下一版 Travel Planning 架构的核心原则。
而且如果按这个模型继续往下设计，我们下一步其实已经不是讨论“该不该用 web_fetch”了，而是应该设计 PlanningContextRequirement 到底有哪些正式类型，以及 Context Acquisition Router 怎么映射 POI / Maps / Web / Research。这会直接决定下一版架构是否真正收敛。
