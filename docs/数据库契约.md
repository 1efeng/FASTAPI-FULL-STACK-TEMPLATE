# Travel Agent v8 数据库契约

> 更新时间：2026-08-13  
> 数据库：PostgreSQL  
> ORM：SQLAlchemy 2.x Async  
> Migration：Alembic  
> 适用阶段：P0 Business Persistence / Request Lifecycle

---

# 1. 文档职责

本文定义 Travel Agent v8 的 durable data ownership、核心业务表、关系、约束、索引、状态迁移与删除策略。

系统中 PostgreSQL 分为两个独立 ownership domain：

```text
Managed PostgreSQL
├── travel_agent_business
└── litellm
```

可以部署在同一个 PostgreSQL 实例，但 schema / database / DB user / migration ownership 必须分离。

> 【历史】v7 曾规划第三个 ownership domain `langgraph_persistence`（M5 LangGraph Persistence，由官方 LangGraph PostgreSQL checkpointer / AsyncPostgresSaver 拥有）。v8 clean baseline 已 SUPERSEDED：durability 由 PostgreSQL / Redis Stream / DBOS(后续) 承担，不再创建 checkpoint domain。

# 3. 项目统一数据库约定

当前项目所有 Business Model 继承：

```python
BaseModel
```

因此自动拥有：

```text
id UUID PRIMARY KEY
created_at TIMESTAMPTZ NOT NULL
updated_at TIMESTAMPTZ NOT NULL
```

新业务表继续沿用该约定。

物理表名继续遵循当前项目 singular convention：

```text
user
item
conversation
message
request_run
business_llm_usage
```

路线图里的 `conversations / messages / request_runs` 是逻辑实体名称，不代表必须使用复数物理表名。

# 4. 核心关系

```text
user
 │
 └── 1:N conversation
          │
          ├── 1:N request_run
          │       │
          │       └── 1:N message
          │             P0 实际为:
          │             1 user + 0/1 assistant
          │
          └── 1:N message
```

关键原则：

```text
Business Conversation 独立于 Agent Runtime session
Business Message 独立于 Agent Runtime 内部消息/状态
RequestRun.id == request_id
```

# 5. conversation

产品层的一次用户对话。

推荐结构：

```text
conversation
──────────────────────────────────────
id                    UUID PK
user_id               UUID NOT NULL FK user.id
title                  VARCHAR(255) NULL
last_message_at        TIMESTAMPTZ NULL
deleted_at             TIMESTAMPTZ NULL
created_at             TIMESTAMPTZ NOT NULL
updated_at             TIMESTAMPTZ NOT NULL
```

> 【历史】v7 曾包含 `langgraph_thread_id UUID NOT NULL UNIQUE` 字段（LangGraph runtime thread 映射）。v8 clean baseline 已移除：Business domain 不再保存 Agent Runtime session 映射。

## 5.1 user_id

Ownership 字段。

```text
FK user.id
ON DELETE CASCADE
```

所有 Conversation API 必须按：

```text
conversation.id
+
current_user.id
```

一起查询。

客户端持有 conversation id 不代表拥有资源。

## 5.2 title

P0：

```text
NULL
→ 首条消息后异步/同步生成标题
```

不要因为标题生成失败阻塞 Chat 主链路。

## 5.3 last_message_at

用于 Conversation List 的产品排序。

每次 durable：

```text
user message
assistant final
```

后更新。

不要用 `updated_at` 代替其业务语义，因为改标题等操作不应该改变“最近聊天时间”。

## 5.4 deleted_at

P0 采用 soft delete。

普通查询必须：

```text
deleted_at IS NULL
```

真正 hard purge 由 retention / privacy policy 处理。

## 5.5 索引

推荐：

```sql
INDEX active conversation list:
(user_id, last_message_at DESC, id)
WHERE deleted_at IS NULL
```

不要额外创建能被上述复合索引覆盖、但没有查询证据的重复索引。

# 6. request_run

一次昂贵 Agent 执行的业务生命周期记录。

**RequestRun.id 就是架构里的 `request_id`。**

推荐结构：

```text
request_run
──────────────────────────────────────
id                    UUID PK  ← request_id
user_id               UUID NOT NULL FK user.id
conversation_id       UUID NOT NULL FK conversation.id
idempotency_key       VARCHAR(255) NOT NULL
status                VARCHAR(16) NOT NULL
started_at            TIMESTAMPTZ NOT NULL
deadline_at           TIMESTAMPTZ NOT NULL
finished_at           TIMESTAMPTZ NULL
error_code            VARCHAR(64) NULL
created_at             TIMESTAMPTZ NOT NULL
updated_at             TIMESTAMPTZ NOT NULL
```

## 6.1 为什么同时保存 user_id 与 conversation_id

`user_id` 是有意的 ownership denormalization。

价值：

```text
Request Status API 可以直接鉴权
Idempotency 可以 user scoped
审计查询不必先 join conversation
```

Service 创建 RequestRun 前必须确认：

```text
conversation.user_id == current_user.id
```

## 6.2 idempotency_key

客户端每次新的“发送”动作生成。

Retry 同一个网络动作：

```text
复用相同 Idempotency-Key
```

真正新的 Regenerate / 新用户消息：

```text
生成新 Idempotency-Key
```

数据库唯一约束：

```sql
UNIQUE (user_id, idempotency_key)
```

这是最终幂等正确性来源。

Redis 可以做快速保护，但不能替代数据库唯一约束。

## 6.3 status

P0 只允许：

```text
running
completed
failed
cancelled
```

数据库推荐：

```text
VARCHAR + CHECK
```

而不是 PostgreSQL native ENUM。

原因：

```text
后续新增状态 migration 更简单
Python 可继续使用 StrEnum
DB 仍有合法值约束
```

推荐：

```sql
CHECK (
  status IN ('running', 'completed', 'failed', 'cancelled')
)
```

## 6.4 状态机

唯一合法迁移：

```text
running
 ├── completed
 ├── failed
 └── cancelled
```

禁止：

```text
completed → failed
completed → cancelled
failed → running
cancelled → completed
```

所有终态更新使用 conditional update：

```sql
UPDATE request_run
SET ...
WHERE id = :request_id
  AND status = 'running';
```

只有成功修改一行的执行方获得 terminal transition。

这可以处理：

```text
cancel vs final race
timeout vs final race
duplicate worker
```

## 6.5 started_at / deadline_at / finished_at

```text
started_at
→ Product Request 真正开始

deadline_at
→ started_at + absolute request deadline

finished_at
→ completed / failed / cancelled 的统一终态时间
```

不要继续使用 `completed_at` 表示所有终态，因为 failed/cancelled 并不是 completed。

推荐约束：

```sql
CHECK (
  (status = 'running' AND finished_at IS NULL)
  OR
  (status IN ('completed', 'failed', 'cancelled') AND finished_at IS NOT NULL)
)
```

`deadline_at` 同时为未来 stale-running recovery 提供索引基础。

## 6.6 error_code

只保存 Product Error Code，例如：

```text
REQUEST_DEADLINE_EXCEEDED
MODEL_UNAVAILABLE
AGENT_LOOP_LIMIT_REACHED
TOOL_REQUIRED_DATA_UNAVAILABLE
INTERNAL_ERROR
```

不要持久化 Provider raw exception / secret / full stack trace 到这个字段。

## 6.7 同一 Conversation 只允许一个 running

P0 不支持一个 Conversation 同时执行两个 Agent Run。

数据库最终兜底：

```sql
CREATE UNIQUE INDEX uq_request_run_one_running_per_conversation
ON request_run (conversation_id)
WHERE status = 'running';
```

上层同时使用 Redis concurrency guard。

两层职责：

```text
Redis
→ 快速拒绝 / UX / distributed runtime

PostgreSQL
→ correctness invariant
```

## 6.8 其他索引

推荐：

```sql
UNIQUE (user_id, idempotency_key)

INDEX (conversation_id, created_at DESC)

INDEX (deadline_at)
WHERE status = 'running'
```

最后一个用于：

```text
stale running detection
deadline recovery job
```

# 7. message

Business Message 只保存用户产品历史。

P0 不保存 Agent Runtime 内部：

```text
ToolMessage
SystemMessage
SubAgent scratchpad
private reasoning
runtime durable state
```

推荐结构：

```text
message
──────────────────────────────────────
id                    UUID PK
seq                   BIGINT IDENTITY UNIQUE NOT NULL
conversation_id       UUID NOT NULL FK conversation.id
request_id            UUID NOT NULL FK request_run.id
role                  VARCHAR(16) NOT NULL
content               TEXT NOT NULL
created_at             TIMESTAMPTZ NOT NULL
updated_at             TIMESTAMPTZ NOT NULL
```

## 7.1 role

P0 只允许：

```text
user
assistant
```

推荐：

```sql
CHECK (role IN ('user', 'assistant'))
```

Tool / System / SubAgent messages 属于 Agent Runtime，不进入 Business Message。

## 7.2 content

P0：

```text
user
→ plain text / Markdown compatible text

assistant
→ Markdown Contract final
```

使用 PostgreSQL `TEXT`，不要使用 VARCHAR(几千) 给旅行计划设置人为长度上限。

## 7.3 request_id

FK：

```text
request_run.id
```

因为：

```text
RequestRun.id == request_id
```

同一次执行：

```text
1 user message
0/1 assistant final
```

数据库推荐：

```sql
UNIQUE (request_id, role)
```

作用：

```text
网络 retry
worker retry
final commit race
```

都不能插入第二条 assistant final。

## 7.4 seq

UUID 与 timestamp 都不是最理想的稳定消息排序键。

因此推荐增加：

```text
seq BIGINT GENERATED ... AS IDENTITY
```

它：

```text
不是公开 Message ID
不参与 Authorization
只用于稳定排序
```

Conversation history：

```sql
WHERE conversation_id = :conversation_id
ORDER BY seq ASC
```

这样不需要实现复杂的 per-conversation counter/lock。

## 7.5 Message Immutable

P0 message 是 append-only。

不要：

```text
UPDATE message.content
```

Regenerate：

```text
创建新的 RequestRun
产生新的 durable message
```

如果未来真正启用 branch/edit，需要单独设计：

```text
message branch lineage
```

不要现在提前加入 `parent_message_id` 等字段。

## 7.6 索引

```sql
UNIQUE (request_id, role)

INDEX (conversation_id, seq)
```

PostgreSQL 不会因为 Foreign Key 自动创建读取索引，因此必须显式检查实际查询路径。

# 8. Business Write Lifecycle

这是三张表最重要的 Contract。

## 8.1 第一个事务：Agent 执行前 durable

收到用户发送：

```text
BEGIN

1. SELECT conversation
   WHERE id = :conversation_id
     AND user_id = :current_user
     AND deleted_at IS NULL

2. INSERT request_run
   status = running

3. INSERT message
   role = user
   request_id = request_run.id

4. UPDATE conversation.last_message_at

COMMIT
```

**只有 COMMIT 成功后才允许调用 Agent。**

因此：

```text
user message durable before Agent
```

不是“先 insert、还没 commit 就调用 Agent”。

## 8.2 Agent Execution

```text
AgentExecutor
（v8 clean baseline 暂无实现，Pydantic AI 下一里程碑接入）
```

执行过程中产生的 Agent Runtime durable state：

```text
由 PostgreSQL / Redis Stream / DBOS(后续) 承担
与 Business Transaction 独立
```

不要打开一个数据库事务等待几十秒 Agent 完成。

## 8.3 成功事务

Agent 成功返回最终回答：

```text
BEGIN

1. INSERT assistant message
   request_id = same request_run.id

2. UPDATE request_run
   SET status = completed,
       finished_at = now()
   WHERE id = :request_id
     AND status = running

3. assert exactly 1 RequestRun row updated

4. UPDATE conversation.last_message_at

COMMIT
```

之后：

```text
send stream finish/final completion
```

因此 Product 完成条件是：

```text
assistant message durable
+
request_run completed durable
+
COMMIT
```

而不是：

```text
模型已经生成最后一个 token
```

## 8.4 Failed

```text
BEGIN

UPDATE request_run
SET status = failed,
    error_code = :product_error_code,
    finished_at = now()
WHERE id = :request_id
  AND status = running

COMMIT
```

P0 不要求为了错误而插入伪 assistant message。

Frontend 根据：

```text
RequestRun status/error
```

渲染失败状态。

## 8.5 Cancelled

```text
UPDATE request_run
SET status = cancelled,
    finished_at = now()
WHERE id = :request_id
  AND status = running
```

如果 final 已经先 durable：

```text
UPDATE 0 rows
```

取消方不得覆盖 completed。

# 9. Crash / Stale Running

存在这种真实故障：

```text
user + request_run durable
↓
COMMIT
↓
worker/process crash
↓
Agent 未开始或未完成
↓
request_run 卡在 running
```

因此 P0 设计必须保留：

```text
deadline_at
```

并在后续 Product Lifecycle milestone 实现 stale-running recovery policy。

推荐：

```text
status = running
AND deadline_at < now()
```

进入 recovery candidate。

最终 error code 可以统一成：

```text
REQUEST_DEADLINE_EXCEEDED
```

或专门：

```text
REQUEST_EXECUTION_LOST
```

具体 Product Error Code 由 `错误契约.md` 决定。

```text

GET    /conversations
GET    /conversations/{id}
PATCH  /conversations/{id}
DELETE /conversations/{id}
```

所有操作必须：

```text

```

```text
WHERE user_id = current_user.id
  AND deleted_at IS NULL
ORDER BY last_message_at DESC NULLS LAST, created_at DESC
```

## Detail

返回 Business Messages。

不要从 Agent Runtime 的 durable state 直接构建用户历史，用户历史只来自 message 表。

## PATCH

P0 主要：

```text

```

## DELETE

soft delete：

```text

```

删除后：

```text
禁止继续发送消息
```

Agent Runtime durable state（Redis Stream / 后续 DBOS 数据）的清理由 retention/delete workflow 处理。

# 11. Request Status API

P0 必须提供 durable recovery endpoint。

推荐语义：

```text
GET /api/v1/chat/requests/{request_id}
```

或最终由 `接口契约.md` 锁定等价路径。

查询必须：

```text
request_run.id = request_id
AND request_run.user_id = current_user.id
```

返回最少：

```json
{
  "request_id": "...",
  "conversation_id": "...",
  "status": "running|completed|failed|cancelled",
  "error_code": null,
  "started_at": "...",
  "finished_at": null
}
```

如果 completed，可以：

```text
frontend refetch conversation/messages
```

不要把完整 assistant final 再复制一份到 `request_run`。

# 12. Ownership / IDOR

禁止：

```text
SELECT conversation WHERE id = :id
然后相信 client user_id

SELECT request_run WHERE id = :request_id
不校验 owner
```

必须：

```text
Business API 从 authenticated current_user 得到 user_id
```

客户端提交：

```text
user_id
```

一律不能作为 Authorization Proof。

P0 不要求 PostgreSQL Row Level Security。

应用层 AuthZ + Integration Tests 是当前 Owner。

# 13. Deletion

## soft delete conversation

立即：

```text
conversation.deleted_at = now()
```

Business messages/request_runs 暂时保留用于：

```text
undo window
audit
retention workflow
```

## hard purge

达到 retention / privacy 条件后：

```text
conversation
→ message
→ request_run
```

可以通过数据库 `ON DELETE CASCADE` 做最终删除。

Agent Runtime durable state：

```text
按 runtime lifecycle / retention workflow 清理
```

不要直接写 SQL 删除 runtime 内部数据。

Usage：

```text
按数据治理策略删除或去标识
```

# 22. 核心不变量

必须始终成立：

```text
1. user message COMMIT before Agent starts
2. assistant final + request completed in one business transaction
3. only one running request per conversation
4. one request has at most one user and one assistant business message
5. RequestRun.id == request_id
6. Idempotency uniqueness enforced by PostgreSQL
7. terminal RequestRun is immutable
8. Business Conversation 独立于 Agent Runtime session
9. Business Message 独立于 Agent Runtime 内部状态
10. client IDs never prove ownership
```

这些 invariant 比具体 ORM 写法更重要。
