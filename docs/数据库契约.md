# 数据库契约

> PostgreSQL 是 durable truth，但不同框架的数据必须保持 **ownership isolation**。

# 1. 三个逻辑数据域

```text
Managed PostgreSQL
├── travel_agent_business
├── langgraph_persistence
└── litellm
```

可以部署在同一个 PostgreSQL 服务，也可以未来拆分；第一阶段重点是 schema/database/user/migration ownership 分开。

# 2. Business Domain

应用自己拥有。

## users

建议核心：

```text
id
status
created_at
updated_at
```

身份 Provider 等字段以 Auth 方案为准。

## conversations

```text
id
user_id
title
created_at
updated_at
deleted_at
```

索引至少围绕：

```text
(user_id, updated_at)
```

## messages

```text
id
conversation_id
role
content
request_id
created_at
```

完整计划第一阶段仍以 message/Markdown 为主。

## request_runs

```text
id
user_id
conversation_id
idempotency_key
status
started_at
completed_at
error_code
created_at
updated_at
```

唯一约束至少：

```text
(user_id, idempotency_key)
```

状态：

```text
running
completed
failed
cancelled
```

## business_llm_usage

这不是 LiteLLM SpendLogs 的复制。

建议：

```text
id
litellm_call_id
request_id
trace_id
user_id
conversation_id
agent_role
logical_model
actual_model
input_tokens
output_tokens
total_tokens
cost
currency
status
created_at
```

`litellm_call_id` 应支持去重。

P0 不要求自己维护 unit-price / pricing-version 引擎。

# 3. LangGraph Persistence Domain

由 LangGraph 官方 PostgreSQL checkpointer 管理。

原则：

- 使用官方初始化 / setup；
- Application 不创建模拟 LangGraph 内部 tables；
- 不直接依赖内部 table 结构做业务查询；
- thread/checkpoint 生命周期通过 LangGraph API 管理；
- 独立 DB user/schema 权限更清晰。

# 4. Business vs Checkpoint

两者不同：

```text
Business Message
→ 用户产品历史与最终结果

LangGraph Checkpoint
→ Agent graph execution state
```

不要只依赖 checkpoint 作为用户可见 conversation truth，也不要复制 checkpoint state 到自研 checkpoint 表。

# 5. Final Commit

业务成功：

```text
BEGIN
insert assistant message
update request_run = completed
COMMIT
SSE final
```

LangGraph checkpoints 在 Agent 执行期间由 checkpointer 自己持久化。

# 6. LiteLLM Domain

LiteLLM 按启用功能管理自己的：

- keys；
- users/teams（Gateway 内部语义）；
- budget；
- spend；
- config / internal state。

不要让 Travel Agent migration 修改 LiteLLM 内部表。

# 7. Redis 与 PostgreSQL 边界

PostgreSQL：

- conversation；
- messages；
- request_runs；
- usage attribution；
- durable state。

Redis：

- rate limit；
- quota；
- concurrency；
- short-lived locks/state；
- LiteLLM shared runtime state。

# 8. Deletion

用户删除 conversation 时：

1. 删除 / soft-delete business conversation/messages；
2. 按数据治理策略处理关联 request_runs；
3. 明确关联 LangGraph thread/checkpoints 清理策略；
4. Usage 是否保留匿名化统计由 retention policy 决定；
5. 不直接删除 LiteLLM 全局 spend 数据而破坏财务核账，按隐私策略做必要去标识。

# 9. Migration

三类 migration 分开：

```text
Business migration
LangGraph checkpointer bootstrap/migration
LiteLLM migration
```

Release 必须明确执行顺序与 rollback compatibility。

# 10. Backup / Restore

P0 必须：

- automated backup；
- retention；
- restore procedure；
- restore drill；
- 恢复后验证 business + LangGraph + LiteLLM 关键数据可用。

“有备份”但没验证 Restore，不算生产完成。

# 11. Pool / Index

连接池和索引通过压测决定，不从 DAU 直接拍数字。

必须监控：

- pool utilization；
- wait time；
- slow query；
- errors；
- disk / storage growth。
