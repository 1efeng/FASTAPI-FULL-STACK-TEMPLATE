# 行伴 Travel Agent v7 架构文档

> 文档状态：2026-08-10 最新架构基线  
> 系统阶段：CLI Agent 核心链路已形成，生产 P0 尚未完成  
> 统一设计目标：**最低 10,000 DAU 的 C 端生产系统**  
> 核心约束：业务单体优先、无状态多实例、共享状态外置、成熟框架优先、禁止重复造轮子。

# 1. 文档目标

本文回答五个问题：

1. 当前 CLI 项目真实存在什么；
2. 未来 10,000 DAU C 端生产形态是什么；
3. Main / Researcher / Tool / Framework / Infrastructure 分别负责什么；
4. 哪些能力由成熟框架直接承担，Travel Agent 不重复实现；
5. 从当前 CLI 到生产系统的 P0 演进顺序是什么。

本文是 **系统架构 Source of Truth**。产品行为看 `产品文档.md`，实现约束看 `开发文档.md`。

# 2. 系统定位

行伴是面向 C 端用户的通用旅行 Agent，核心能力包括：

- 普通旅行问答；
- 当前旅行事实查询；
- 多日完整旅行规划；
- 基于已有计划的自然语言修改；
- 预算确定性汇总；
- 辅助币种换算；
- 后续扩展为可稳定运营、可观测、可控制成本、可横向扩展的在线系统。

系统不以“Agent 数量多”为目标，而以用户得到**可信、可执行、可修改、可恢复**的旅行计划为目标。

---

# 3. 10,000 DAU 的含义

10,000 DAU 是**架构设计下限**，不是固定 QPS、固定 SSE 连接数或固定服务器数量。

必须满足：

```text
应用可无状态多实例
关键状态不依赖单进程内存
模型和 Tool 故障有明确 Owner
请求具备幂等、Deadline、可恢复状态
会话可跨实例 / 跨设备恢复
AI Token / Cost / Error 可定位
生产数据可备份并验证恢复
上线前有自动 Eval、压测和安全 Gate
```

最终实例数、连接池、SSE 并发、LLM 并发等通过压测和灰度数据决定。

**10,000 DAU 不等于微服务。** 第一阶段保持业务 Modular Monolith + Stateless Multi-instance。

# 4. 总体设计原则

## 4.1 语义决策与确定性边界分离

> 模糊、概率性的语义判断交给模型；确定性的规则、计算、状态和基础设施边界交给代码与成熟组件。

```text
模型负责
├── 理解用户意图
├── 判断是否需要澄清
├── 旅行方案取舍
├── Research 信息压缩
└── 最终旅行计划表达

代码 / 基础设施负责
├── Auth / Authorization
├── Idempotency
├── Request Deadline
├── Rate Limit / Quota
├── LLM Routing / Retry / Fallback
├── Tool Timeout / Degradation
├── Budget Math
├── FX 调用
├── Persistence
├── Trace / Metrics
└── Backup / Restore
```

## 4.2 Agent 按“独立认知上下文”拆，不按功能拆

当前业务 Agent 只有：

```text
Main Agent
travel-researcher SubAgent
```

不会因为预算、天气、签证、货币、RAG 等能力各自创建 Agent。

默认禁止新增：

```text
Planner Agent
Writer Agent
Validator Agent
Budget Agent
Currency Agent
Weather Agent
Visa Agent
RAG Agent
```

除非未来出现真正独立的认知上下文、独立伸缩或独立 SLA，并通过 ADR 修改架构。

## 4.3 成熟框架优先

如果框架已经稳定提供能力，不在业务项目中重造。

当前正式 Owner：

| 能力 | Owner |
|---|---|
| Agent Harness / SubAgent / Context Isolation | Deep Agents |
| Agent Checkpoint / Thread Persistence | LangGraph Checkpointer |
| LLM Gateway / Retry / Fallback / Routing / Spend | LiteLLM Proxy |
| AI Trace / Dataset / Eval / Experiment | LangSmith |
| Infrastructure spans / propagation | OpenTelemetry instrumentation（标准协议，不是独立平台） |
| HTTP / Native SSE | FastAPI |
| Business Durable State | PostgreSQL |
| Business Runtime Shared State | Redis |
| Product Logic / Business Policy | Travel Agent |

# 6. Agent Cognitive Core

## 6.1 Main Agent

Main 是唯一最终语义 Owner。

负责：

- 理解用户真实请求；
- 区分闲聊 / 单点事实 / 完整规划 / 修改计划；
- 只澄清真正改变整体方案的条件；
- 选择最终路线、节奏、交通、住宿和活动；
- 决定最终采用的方案；
- 调用确定性预算和汇率能力；
- 输出最终回答。

Main 不负责：

- 自己实现模型容灾；
- 自己实现 checkpoint；
- 自己计算多项金额总和；
- 在完整规划阶段直接执行高噪声 Research；
- 把模型记忆当实时旅行事实。

## 6.2 Travel Planning Skill

`travel-planning` 是规划方法与输出 Contract，不是 Planner Agent。

负责：

- 完整规划的方法；
- 创建 / 修改计划的共同约束；
- Research 前后职责边界；
- Markdown Contract。

不创建固定 LangGraph Planning Workflow。

## 6.3 travel-researcher

Researcher 是完整规划唯一的 Research Workspace。

拥有：

```text
search_travel_info
search_maps
get_weather
```

负责：

- 当前交通规则；
- 路线 / 距离 / 耗时；
- 开放 / 预约；
- 门票 / Pass；
- 天气 / 季节；
- 其他影响执行性的当前事实；
- 将高噪声 Tool Context 压缩为 Research Findings。

不负责：

```text
最终路线
最终 Day-by-Day 计划
预算总和
汇率换算
最终用户回答
```

## 6.4 完整规划职责链

```text
User
 ↓
Main
 ↓
必要澄清
 ↓
travel-planning Skill
 ↓
travel-researcher
 ↓
Research Findings
 ↓
Main 选定最终方案
 ↓
calculate_budget（按需）
 ↓
convert_currency（按需）
 ↓
Markdown Contract
 ↓
Main Final
```

这是职责 Contract，不是固定 Workflow Graph。

# 7. Framework Ownership

这是本版本最大的架构收敛。

## 7.1 Deep Agents：Agent Harness / Context Owner

Deep Agents 负责：

- Agent Harness；
- Skills；
- SubAgent；
- Context Isolation；
- 大型 Tool 输入 / 输出 offloading；
- 接近 Context Window 时的自动 Summarization；
- Context Overflow 恢复（满足版本要求时）。

因此 Travel Agent **不自研通用 Context Compression Engine**。

注意：当前仓库依赖历史基线为 `deepagents>=0.7.4`；最新版 Deep Agents 的完整自动 Summarization / 精确 token counting / ContextOverflow 恢复能力需要更高版本。正式依赖升级必须先锁版本并通过 Unit / Integration / Eval。

业务层仍需定义：

- 最新完整计划是什么；
- 哪些用户约束属于关键业务语义；
- 哪些信息必须在压缩后仍可恢复。

## 7.2 LangGraph：Checkpoint Owner

生产环境使用官方 PostgreSQL Checkpointer：

```text
langgraph-checkpoint-postgres
AsyncPostgresSaver
```

LangGraph 自己管理：

- checkpoints；
- checkpoint writes；
- thread state；
- super-step persistence；
- pending writes recovery；
- resume / fault tolerance。

Travel Agent **不自己设计 checkpoint 表结构，不复制 LangGraph checkpoint 数据模型**。

业务 PostgreSQL 与 LangGraph-managed tables 是不同职责：

```text
Business Tables
├── users
├── conversations
├── messages
├── request_runs
└── business_usage_attribution

LangGraph-managed persistence
└── AsyncPostgresSaver tables
```

## 7.3 LiteLLM Proxy：LLM Infrastructure Owner

生产正式选型：

> **LiteLLM Proxy Server = Central LLM Gateway**

Travel Agent 不再直接持有生产 Provider Secret，也不直接决定具体 Provider retry / failover。

LiteLLM 负责：

- OpenAI-compatible unified interface；
- 多 Provider / 多 deployment；
- bounded retries；
- model group fallback；
- timeout；
- health checks；
- reactive cooldown；
- health-aware routing；
- RPM / TPM / max parallel；
- Virtual Keys；
- service / key / team budget；
- spend tracking；
- actual model / call metadata；
- provider abstraction。

架构不再要求 Travel Agent 自研传统 `CLOSED/OPEN/HALF_OPEN` Circuit Breaker。

LiteLLM 的实际隔离语义采用：

```text
Failure
 ↓
allowed_fails / failure policy
 ↓
Deployment Cooldown
 ↓
Health Check / Routing Pool
 ↓
Fallback Model Group
```

## 7.4 LangSmith：AI Trace 与 Eval Owner

LangSmith 负责：

- Agent Trace；
- Main / Researcher trajectory；
- Tool Calls；
- Dataset；
- Evaluators；
- Offline Experiments；
- Online Evaluation；
- Trajectory Evaluation。

Travel Agent 不自研 Eval 平台 / Trace UI / Experiment 管理平台。

## 7.5 OpenTelemetry：基础设施 Span 标准协议与 Instrumentation

统一：

```text
request_id = Travel Agent 业务请求 ID
trace_id   = OpenTelemetry Trace ID
span_id    = OpenTelemetry Span ID
litellm_call_id = LiteLLM 每次模型调用 ID
```

禁止再自定义第四套“内部 trace_id”。

## 7.6 FastAPI：HTTP / Native SSE Owner

正式 API 使用 FastAPI。

当依赖版本满足 `FastAPI >= 0.135.0` 时，直接使用：

```python
fastapi.sse.EventSourceResponse
fastapi.sse.ServerSentEvent
```

使用 FastAPI 原生：

- SSE 编码；
- event / id / retry；
- keep-alive ping；
- `Cache-Control: no-cache`；
- `X-Accel-Buffering: no`。

Travel Agent 只定义业务事件 Contract，不自研 SSE wire protocol。

# 9. 请求生命周期

## 9.1 Request-level Deadline Owner

整体用户请求 Deadline 属于 FastAPI / Application，不属于 LiteLLM。

原因：一次用户请求可能包含多次 LLM Call + 多次 Tool Call。

```text
User Request Deadline
       │
       ├── Main LLM Call
       ├── Researcher LLM Call
       ├── Search
       ├── Maps
       └── Main Final LLM Call
```

每次外部调用都不得超过“剩余 Deadline”。

LiteLLM 只管理单次 LLM 调用内部的：

- timeout；
- retry；
- fallback；
- provider isolation。

## 9.2 标准请求流程

```text
Client
 ↓
Nginx / LB
 ↓
FastAPI
 ↓
Authentication
 ↓
Resource Authorization
 ↓
Redis Business Rate Limit / Quota / Concurrency
 ↓
Idempotency-Key
 ↓
Create request_id + OTel root span
 ↓
Business Transaction:
  persist user message
  request_run = in_progress
 ↓
Travel Agent Execution
 ↓
LangGraph AsyncPostgresSaver
  在 Agent super-step 生命周期中独立 checkpoint
 ↓
Main / Researcher
 ↓
LiteLLM + Tool Providers
 ↓
LangSmith / OTel / LiteLLM Spend
 ↓
Agent 成功返回 Final
 ↓
Business Transaction:
  persist assistant message
  request_run = completed
 ↓
COMMIT
 ↓
SSE final
```

重要修正：

> 不再把“Assistant Final + LangGraph checkpoint + request_run”描述成同一个业务 SQL transaction。

LangGraph checkpoint 按其自身执行生命周期写入；业务最终完成状态只以业务 message / request_run commit 为准。

## 9.3 Final Durable Before SSE Final

必须满足：

```text
Assistant Final durable
+
request_run completed durable
        ↓
DB COMMIT
        ↓
SSE final
```

如果 SSE 最终事件丢失，客户端可以通过 request status / conversation 恢复已完成结果。

## 9.4 Idempotency

```text
same user + same idempotency_key

running   → 返回同一个 request 状态
completed → 返回已有结果
failed    → 按明确策略允许新 retry request
```

网络重试不能重新启动昂贵 Agent 执行。

# 10. Persistence 与 Memory

## 10.1 Business Persistence

业务 PostgreSQL保存：

```text
users
conversations
messages
request_runs
business_usage_attribution
```

第一阶段完整旅行计划继续作为 message / Markdown 保存，不引入重型 Plan CRUD。

## 10.2 LangGraph Checkpoint

Agent thread / checkpoint 使用：

```text
AsyncPostgresSaver
```

不由业务 ORM 建模。

## 10.3 Deep Agents Context Management

不自研通用摘要引擎。

优先使用 Deep Agents 当前版本提供的：

```text
Context Isolation
Offloading
Automatic Summarization
Context Overflow Recovery
```

业务层只负责提供关键上下文语义和配置边界。

## 10.4 Long-term Product Memory

如果未来需要跨 thread 用户长期偏好，使用明确的 Business Memory / LangGraph Store 设计，不要把所有历史 conversation 强行拼入 Prompt。

# 11. LLM Gateway 设计

## 11.1 生产调用路径

开发可保留直接 Provider 模式，但生产默认：

```text
Travel Agent
 ↓
OpenAI-compatible client
 ↓
LiteLLM Proxy
 ↓
Logical Model Group
 ↓
Provider Deployment
```

应用生产配置只需要知道：

```text
LITELLM_BASE_URL
LITELLM_API_KEY
LLM_MODEL_GROUP
```

Provider Secrets 在 LiteLLM 层管理。

## 11.2 LiteLLM 逻辑模型组

P0 可先：

```text
travel-agent
  Primary   → DeepSeek
  Fallback  → OpenAI / Other
```

P1 Role-based Routing 再演进：

```text
travel-main
travel-research
```

业务角色选什么“逻辑模型组”由 Travel Agent Policy 决定；逻辑模型组内部 deployment / provider 路由由 LiteLLM 决定。

## 11.3 Retry Owner

```text
LiteLLM = LLM retry / fallback Owner
```

必须避免：

```text
Provider SDK retry × LangChain model retry × LiteLLM retry
```

应用客户端只保留连接级安全策略，不叠加高次数模型 retry。

## 11.4 Gateway HA

生产要求：

- LiteLLM Proxy 2+ replicas 或等价托管 HA；
- 共享 Redis；
- LiteLLM PostgreSQL；
- pinned version / image digest；
- readiness / liveness；
- migration / rollback；
- secrets 不进入应用日志。

# 12. LLM Cost 与 Business Attribution

LiteLLM 是模型基础设施成本事实源，负责：

- tokens；
- actual model；
- response cost；
- spend logs；
- key / team / model group budget。

Travel Agent 不再实现独立 pricing engine。

业务数据库保留**薄归因表**：

```text
business_usage_attribution
├── id
├── litellm_call_id
├── request_id
├── trace_id
├── user_id
├── conversation_id
├── agent_role
├── source
├── logical_model_group
├── actual_model
├── input_tokens
├── output_tokens
├── cost
├── status
└── created_at
```

职责：

```text
LiteLLM：这次模型调用花了多少钱
Travel Agent：这笔钱属于哪个用户 / Request / Agent Role / 产品功能
```

不再要求 Travel Agent 自己维护：

```text
input_unit_price
output_unit_price
pricing_version
```

除非未来财务核账确实需要独立快照。

# 13. Rate Limit 与 Budget 双层设计

## Product Layer — Travel Agent / Redis

负责：

- User 请求频率；
- IP 防刷；
- 每用户每日 AI quota；
- 用户并发；
- 套餐 / 产品权益；
- Idempotency。

## LLM Infrastructure Layer — LiteLLM

负责：

- Virtual Key；
- model access；
- RPM / TPM；
- max parallel；
- service / key budget；
- provider capacity。

```text
Product Quota != LLM Infrastructure Limit
```

两层都保留。

# 14. Tool Resilience

LiteLLM 只保护 LLM，不保护 Search / Maps / Weather / FX。

每个外部 Tool 至少需要：

```text
per-tool timeout
retryable error taxonomy
bounded retry
provider fallback（存在时）
cancellation
standard ToolError
source / fetched_at metadata
partial degradation
```

最低降级：

```text
Weather fail
→ 继续规划，标记天气未核实

FX fail
→ 保留当地货币，不猜换算

Maps fail
→ 仅做区域级路线，不承诺精确耗时

Search primary fail
→ provider fallback

全部必要 Research 不可用
→ 明确无法核实，不伪造实时事实
```

---

# 15. Runtime Guard

当前 recursion limit 保留，但升级为三层概念：

```text
Layer 1
LangGraph recursion_limit
→ 防 graph / agent loop

Layer 2
ModelCallLimitMiddleware
→ 防模型调用次数失控

Layer 3
ToolCallLimitMiddleware
→ 防 Search / Maps 等 Tool runaway
```

如果当前安装版本支持对应 Middleware，优先使用官方实现。

注意：Custom SubAgent middleware 不应假设自动继承 Main。所有需要的安全 Middleware 要显式应用到 Main / Researcher。

## 16.3 LiteLLM Telemetry

聚焦：


## 16.4 Platform Monitoring

至少覆盖：

- HTTP QPS / 4xx / 5xx / latency；
- active SSE / disconnect；
- CPU / memory；
- PostgreSQL pool / latency / error；
- Redis pool / latency / error；
- LiteLLM throughput / fallback / cooldown / error；
- Tool provider latency / error；
- structured logs；
- alerting。

LangSmith 负责 Agent/Tool/LLM 语义追踪；平台 HTTP/DB/Redis 指标继续使用现有监控，OTel 只作为可选的 span 标准与 instrumentation，不要求单独建设 OTel 平台。

# 18. Security 与 Data Governance

## 18.1 Authentication != Authorization

```text
Authentication
→ 你是谁

Authorization
→ 这个 conversation / request 是否属于你
```

客户端传入 `user_id / conversation_id / request_id / thread_id` 不能直接作为授权依据。

## 18.2 PII

Agent pipeline 优先复用 LangChain `PIIMiddleware` 等成熟能力处理输入 / 输出 / Tool result 的 PII。

但平台仍独立负责：

- API / structured log redaction；
- LangSmith trace policy；
- LiteLLM logging policy；
- PostgreSQL retention；
- Backup retention；
- 用户删除。

## 18.3 Web Content Boundary

所有 Web Research 内容均为：

```text
Untrusted External Data
```

不得升级为 system / developer instruction，不得泄露 Secret，不得触发越权能力。

# 20. Dependency 与 Version Governance

全程 Vibe Coding 必须禁止“最新文档 + 老依赖”错配。

当前规则：

```text
pyproject.toml
→ compatibility intent

uv.lock
→ exact dependency Source of Truth
```

生产构建使用 frozen / locked sync，不允许部署时临时解析新版本。

Deep Agents 等 pre-1.0 / 高速演进依赖升级必须：

```text
upgrade branch
 ↓
update uv.lock
 ↓
unit tests
 ↓
integration tests
 ↓
Basic Eval
 ↓
CLI smoke
 ↓
gray
```

FastAPI Native SSE 的使用要以实际锁定版本支持为前提。

LiteLLM Docker image 必须 pin tested version / digest，不使用浮动 `latest` 作为生产 Source of Truth。

# 25. 最终架构判断标准

任何生产设计至少回答：

1. 应用能否无状态多实例；
2. Business state 和 Agent checkpoint 是否由正确 Owner 持久化；
3. LiteLLM 是否统一负责 LLM retry / fallback / health；
4. End-to-End Deadline 是否由 Request Lifecycle 负责；
5. Tool 是否有独立 timeout / degradation；
6. request_id / OTel trace / LiteLLM call id 是否可关联；
7. LangSmith 是否承担 AI Trace / Eval 而不是自建平台；
8. LLM 成本是否由 LiteLLM 计算、业务层做归因；
9. 客户端重试是否幂等；
10. final 是否先 durable 再 SSE final；
11. 是否使用 LangGraph production checkpointer；
12. 是否避免重复实现 Deep Agents context management；
13. Auth 与 Authorization 是否分离；
14. 实时事实是否有 source / freshness；
15. PII / Secret / Trace / retention 是否有治理；
16. 依赖是否由 uv.lock / pinned image 锁定；
17. 升级 Prompt / Model / Framework 是否过 Eval；
18. 数据是否可 Backup + Restore；
19. 是否存在不必要的自研基础设施；
20. 是否在没有真实瓶颈前过早微服务化。

# 26. 一句话总结

> **最新 Travel Agent v7 架构不再把生产能力理解为“自己实现一套 AI 基础设施”，而是以 Travel Agent Cognitive Core 为业务核心，复用 Deep Agents 的 Agent/Context、LangGraph 的 Checkpoint、LiteLLM 的 LLM Gateway、LangSmith 的 Trace/Eval、OpenTelemetry 的跨服务 Trace 和 FastAPI 的原生 SSE，再由 PostgreSQL/Redis 承担业务状态，从而用更少自研代码达到最低 10,000 DAU 的可扩展生产基线。**
