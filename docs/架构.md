# 5. 架构决策方法

任何架构决定都必须写清：

```text
Product requirement
→ 需要满足什么产品行为

Observed constraint
→ 有什么真实工程限制 / benchmark / failure evidence

Options
→ 至少有哪些合理方案

Decision
→ 为什么选择当前方案

Rejected alternatives
→ 为什么不选其他方案

Validation
→ 如何用 test / eval / benchmark 证明

Migration impact
→ 对 CURRENT code 的影响
```

不能因为：

```text
“之前就是这么做的”
“某个框架有这个能力”
“多 Agent 看起来更高级”
“单次 benchmark 慢”
```

直接成为架构理由。

# 6. Architecture Change Gate

Architecture Baseline 一旦确认，后续默认冻结。

只有同时满足以下条件才允许修改核心架构：

```text
1. 当前 Product Baseline 无法被现有架构合理满足
2. 有明确代码 / eval / benchmark / incident 证据
3. 局部实现优化无法解决
4. 新方案有明确收益和迁移成本分析
5. 形成新的 ADR
6. 获得明确批准
```

Prompt、Tool routing、Context limit、性能参数和 provider 问题默认先视为实现层问题，不自动升级为架构问题。

# 9. CURRENT Search / Extract 实现证据（2026-08-22）

> 本节只记录当前代码、已批准的局部实现任务和真实回归证据，不回答第 4 节的 TARGET 问题，不代表 Architecture Baseline accepted，也不把当前供应商或执行拓扑冻结为 TARGET。

当前实现采用一条简单的单 Agent 工具链：

```text
用户需求
→ 主模型生成多条互补 query
→ 主模型调用通用 `web_search`，由 Python 工具并发调用 Tavily Search
→ 主模型依据标题、URL、相关性与极简 snippet 粗筛重点来源
→ 主模型调用通用 `web_fetch`，由 Python 工具按同一问题批量调用 Tavily Extract
→ 主模型结合结构化旅行工具形成最终行程
```

当前局部实现不包含 Research Agent、ResearchSummary、embedding、向量库或搜索后的独立摘要步骤。`web_search` 保留 Tavily Search 结果中的极简内容片段，在适配层规范化并截断为最多 100 字符的 `snippet`，连同标题、URL 与相关性分数交给模型粗筛；它不返回 `raw_content` 或完整网页正文。脚本负责确定性的批量调用、失败隔离与结果整理，模型负责生成 query、选择重点链接并通过 `web_fetch` 读取必要内容后最终综合。

模型只感知 `web_search`（发现候选网页）和 `web_fetch`（读取已知网页）两个通用操作，不感知 Tavily 的产品名称。当前只有 Tavily 一个底层实现，没有 Provider 工厂、动态路由、自动回退或多供应商配置；若未来有真实替换需求，再在不改变 Agent 工具契约的前提下引入相应边界。

Search 当前调优参数：

```text
search_depth = basic
include_answer = false
include_raw_content = false
max_results = 5
snippet_max_chars = 100（项目适配层截断，不是 Tavily 原生参数）
```

链接数量不设置项目级硬上限。`chunks_per_source` 只适用于 Tavily 的 `fast` / `advanced` Search，当前 `basic` Search 不传这个无效参数。Search / Extract 工具保持领域无关，只提供批量搜索、聚焦读取和通用结果整理；旅行研究策略由 `travel-skill` 决定。

Extract 当前调优参数：

```text
extract_depth = basic
format = text
chunks_per_source = 2
query = 当前需要核查的具体问题
```

同一问题的候选来源可以批量提取，不同关键问题不混入同一个 Extract。Search 结果只用于发现和筛选候选页面；需要网页内容时读取选中的页面，影响核心行程执行的事实优先读取官方或直接服务提供方页面，并在最终计划中就近引用。

当前相关工程事实：

```text
高德路线已使用 v5 路径规划，并保留城市语境、供应商错误码和成功地理编码缓存
LiteLLM 在 Docker 内使用 http://litellm:4000，宿主机诊断使用 http://localhost:4000
Main 单次运行当前限制为 12 次模型请求、30 次工具调用
Search / Extract 与 Agent 已记录 query、链接数、内容字符数、耗时、错误和 token 指标
```

固定回归输入为：郑州出发、北京 3 天 2 晚、2026-08-26 出发、情侣 2 人、总预算 CNY 5000、偏好休闲/文化/美食。

调整前一次成功基线：

```text
5 条 query
25 个候选链接
Search 返回约 35,355 字符
Extract 0 个链接
5 次模型请求
18 次工具调用
129,060 input tokens
13,091 output tokens
142,151 total tokens
105.4 秒总耗时
```

后续验证比较 Search 字符数、实际 Extract 链接、关键事实来源、Markdown Contract 完整性、模型请求、工具调用、token 与总耗时。只有真实回归证明局部调优仍不足时，才继续讨论更复杂的压缩或检索方案。

本轮调整与回归结果：

| 阶段 | Query / 候选 | Extract | 模型 / 工具 | Token | 耗时 | 结果 |
|:---|:---|:---|:---|:---|:---|:---|
| 原基线 | 5 / 25 | 0 | 5 / 18 | 142,151 | 105.4s | 完成，但没有重点阅读 |
| 缩短片段后 | 13 / 65 | 0 | 9 / 25 | 273,484 | 103.4s | 完成；模型用补搜代替 Extract |
| 仅强化 Skill 后 | 23 / 115 | 0 | 达到 12 次模型请求上限 | 未形成完整统计 | 117.2s | 失败；证明仅靠提示词不能控制错误路径 |
| 每条 query 最多 3 个候选 + 旅行化 Tool 路由 | 13 / 39 | 5 个链接 | 8 / 20 | 201,591 | 139.1s | 完成但劣于原基线；方案已否决并回退 |
| Candidate Plan + MSPC Skill | 6 / 30 | 0 | 8 / 14 | 254,236 | 98.8s | 完成；内容齐全，但 token 明显高于原基线且关键事实未 Extract |
| 仅标题、URL、相关性 | 10 / 50 | 9 个链接 | 8 / 17 | 169,747 | 133.5s | 完成；Search 上下文小，但缺少用于粗筛的片段 |
| 100 字符极简 snippet | 10 / 50 | 11 个链接 | 10 / 30 | 270,335 | 170.9s | 完成且结构齐全；单样本成本上升，另一次运行达到 12 次请求上限 |

被否决的最后一次回归中，Search 返回约 20,971 字符，Extract 返回约 6,667 字符。虽然 Search 内容减少约 41% 并首次读取了重点页面，但总 token 增加约 42%，耗时增加约 32%，证明把领域策略和候选数量硬限制放进通用工具并不能改善整体效率。当前实现已撤销 `max_results=3` 和旅行化 Tool 路由，恢复通用 Search / Extract 接口；该失败数据仅作为反例保留。

随后还验证过“每次 Search 后只暴露 Extract 并强制工具调用”的状态机。测试首轮 6 条 query 返回 30 个候选、约 16,898 字符；在被中止前发生 4 次 Extract 调用，既出现了无关页面、重复 URL，也有两个页面提取失败，其中一次等待约 28 秒。该方案只保证发生 Extract，不能保证选中正确来源，因此已整体删除。当前 Search 与 Extract 始终并列可用，不修改 `tool_choice`，也不在运行时隐藏其他工具；模型依据 Skill 和当前信息缺口自行决定继续搜索、重点读取或直接出稿。

Candidate Plan + MSPC Skill 的单样本真实回归分两轮批量搜索。第一轮查询往返高铁、故宫预约和北京三日经典路线；第二轮查询天安门预约、八达岭交通与门票、前门/王府井住宿。两轮 Search 共返回约 40,128 字符。八达岭最终只作为可选替代出现，故宫查询还加入了用户未提供的“学生”条件，说明模型尚未稳定做到“只搜索当前候选方案的真实缺口”。最终方案结构完整、预算闭合，但没有调用 Extract，也没有为故宫和天安门的预约规则提供就近直接来源。

恢复极简 snippet 后的成功回归共执行 3 次批量 Search：10 条 query 返回 50 个候选，Search 结果约 9,736 字符；4 次 Extract 共读取 11 个页面，返回约 13,450 字符。最终答案的行程概览、行前准备、三天安排、住宿、美食、预算和提醒均完整，预算保持在 CNY 5,000 内。与只返回标题、URL 和相关性时的单样本相比，snippet 提供了粗筛依据，但没有自动减少研究轮次：总 token、工具调用和耗时均上升，且另一次相同输入运行达到 12 次模型请求上限。该结果只证明当前 Search / Fetch 数据契约可用，不证明 100 字符是已经完成性能优化的参数；后续需要用多样本评测判断成本变化来自 snippet、模型随机性还是其他旅行工具调用。

该次运行因现有数据库中的测试用户凭据与容器 `FIRST_SUPERUSER` 环境不一致，HTTP E2E 登录返回 400；为避免修改用户或数据库，指标来自同一生产 `PydanticAIExecutor` 的直接运行。LiteLLM / DeepSeek、Tavily、旅行工具、Skill、UsageLimits 与工具循环均为真实生产链路，仅未覆盖 HTTP 登录和消息持久化。

当前 Skills 运行时采用三级渐进加载：启动时只披露已选择 Skill 的名称和描述，匹配任务后通过 `load_capability` 注入 `SKILL.md`，激活后才允许按相对路径逐个读取该 Skill 的 `references/`、`assets/` 或 `scripts/` 资源。资源路径使用启动时只读清单，并拒绝越界路径、符号链接和超限文件；脚本资源不会自动执行。稳定输出和事实安全所必需的前置规则仍保留在 `SKILL.md`，详细运行合同和示例按需读取。完整回归此前观察到的前置思考文本、个别 Emoji / 裸 `¥`、日期措辞过度确定以及部分关键提醒引用第三方来源，仍属于出稿质量与来源选择问题，不应通过继续增加 Search 次数解决。
