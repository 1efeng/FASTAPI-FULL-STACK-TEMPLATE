# 4. 新架构需要回答的问题

架构设计开始后，必须依次回答，而不是先选框架。

## 4.1 Product cognition

```text
Trip Intent 在系统里是否需要显式表示？
Trip Contract 如何进入一次规划？
Experience Strategy / Candidate Plan 是否需要结构化状态？
如何表达 Minimum Sufficient Planning Context？
如何判断 Context sufficient？
如何支持已有计划的局部修改？
```

## 4.2 Reality acquisition

```text
哪些 Planning Context 可以估算？
哪些需要结构化现实数据？
哪些需要动态公开信息？
哪些需要多来源研究？
如何防止无边界 discovery？
如何避免原始 evidence 污染决策上下文？
```

## 4.3 Execution model

```text
一次请求由什么执行单元完成？
模型自由度应该放在哪里？
确定性代码负责哪些边界？
是否需要多个 Agent / Worker / Workflow？
并发、取消、超时和失败如何传播？
```

## 4.4 Product runtime

```text
会话与用户数据的 Source of Truth 是什么？
请求生命周期如何持久化？
流式响应与业务完成状态如何一致？
如何支持取消、恢复、幂等和多实例？
```

## 4.5 Cost and context

```text
模型调用次数如何观测？
外部 Context 如何控制大小？
何时需要压缩？
如何区分成本优化和架构优化？
```

## 4.6 Trust

```text
哪些事实必须当前可验证？
哪些允许 estimate / range？
来源和不确定性如何表达？
失败时如何降级而不伪造？
```

# 5. 架构决策方法

任何架构决定都必须写清：

```text
Product requirement
→ 需要满足什么产品行为

Observed constraint
→ 有什么真实工程限制 / benchmark / failure evidence

Options
→ 至少有哪些合理方案

Decision
→ 为什么选择当前方案

Rejected alternatives
→ 为什么不选其他方案

Validation
→ 如何用 test / eval / benchmark 证明

Migration impact
→ 对 CURRENT code 的影响
```

不能因为：

```text
“之前就是这么做的”
“某个框架有这个能力”
“多 Agent 看起来更高级”
“单次 benchmark 慢”
```

直接成为架构理由。

# 6. Architecture Change Gate

Architecture Baseline 一旦确认，后续默认冻结。

只有同时满足以下条件才允许修改核心架构：

```text
1. 当前 Product Baseline 无法被现有架构合理满足
2. 有明确代码 / eval / benchmark / incident 证据
3. 局部实现优化无法解决
4. 新方案有明确收益和迁移成本分析
5. 形成新的 ADR
6. 获得明确批准
```

Prompt、Tool routing、Context limit、性能参数和 provider 问题默认先视为实现层问题，不自动升级为架构问题。
